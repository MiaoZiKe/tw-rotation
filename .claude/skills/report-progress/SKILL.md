# 回報進度

> Andy 2026-09-20 定的流程：「幫我將目前交代的任務一一列出，並且有完成的有標示出來，
> 進行中的做到哪裡，未完成的（在等）什麼，後續可以執行的都執行完畢，
> 有重大問題再提問。」
>
> 這支 skill 就是把那段話固定成一套動作。**它不是「寫一份報告」，是「先把能做的做完，
> 再報告」** —— 順序不能反過來。

## 為什麼要有這支

Andy **只重新整理網頁、不按任何本機指令**。他沒有辦法從對話裡判斷我說的「好了」是不是真的，
也看不到我在背景跑了什麼。所以每一次回報都必須是**可自己查證的**：
給他網址、告訴他該看哪裡、以及我自己已經查證到什麼程度。

2026-09-13 有過一次：8 個 commit 沒推上去，他連續四次回報「縮放還在」，
其實每一次都早就改好了。回報如果只講「我做了什麼」而不講「他現在打開網頁會看到什麼」，
那份回報是沒有用的。

## 步驟（照順序做，不要跳）

### 1. 先確認推得上去

```bash
git -C <repo> push --dry-run origin main
```

回 `access denied by the git proxy: ... not in this session's authorized repository set`
就代表這個 session 沒有寫入權限 —— **立刻在回報最上面告訴 Andy**，不要埋頭做。
授權是跟著 session 走的，每個新 session 都要重驗。

### 2. 盤點：現在到底有哪些任務

依序讀，**不要憑記憶列清單**：

1. `HANDOFF.md` 最上面那一段的任務表（這是權威來源）
2. `git log --oneline -20` 對照哪些已經進 repo
3. `git status --short` 看有沒有還沒 commit 的東西
4. 還在跑的背景 agent 與背景指令（有就標成「進行中」，**不要預測它的結果**）

盤點的產出是一張表，每一列都要有：**編號、需求（用 Andy 自己的話）、檔案、狀態**。

### 3. 把還能做的做完（這一步最容易被跳過）

「後續可以執行的都執行完畢」是硬要求。典型的有：

- 已經改好但還沒跑關卡的 → 跑關卡
- 關卡過了但還沒 commit / push 的 → commit + push
- 推上去了但還沒確認部署的 → 等 Actions、確認部署成功
- 背景 agent 已經回報但還沒整合的 → 整合
- 被某件事擋住、但**其他部分不受影響**的 → 把不受影響的做完

**只有真的被「等 Andy 回答」或「等外部系統」擋住的才准留著不做。**

### 4. 三道關卡（推之前，一定）

判斷要跑哪幾道**一律用機器，不准靠記憶**：

```bash
git diff --name-only <上次 push 的 commit>..HEAD
```

- 清單裡出現 `pipeline/`、`tests/`、`scripts/`（`_uitest.py` 除外）、`requirements.txt`、`.github/`
  其中任何一項 → **一定要跑 `pytest tests/ -q`**
- 清單裡完全沒有 `site/**` 也沒有 `pipeline/build_payload.py`
  → `_preview.py` 與 `_uitest.py` 可以跳過
- 只要沾到其中任何一個 → 一定要跑

```bash
python3 -m pytest tests/ -q                       # 約 3.5 分鐘
SKIP_INTRADAY=1 python3 -m pipeline.build_payload # 改了 YAML/pipeline 才需要，約 5 分鐘
python3 scripts/_preview.py                       # 約 2 分鐘
python3 scripts/_uitest.py                        # 約 14 分鐘（交付前一定要完整跑一輪）
```

開發過程中反覆修同一段時可以用 `--only <關鍵字>` 只跑那一段；
**交付前仍然要完整一輪**。多個 agent 同時跑時用 `TW_UITEST_PORT` / `TW_PREVIEW_PORT` 指定不同埠。

**跳過的時候要在回報裡講一聲跳了什麼、為什麼**，不可以默默省掉。

### 5. 推上去，然後確認線上真的換掉了

```bash
git pull --rebase --autostash origin main && git push -u origin main
```

推完**不算交付**。要等 Actions 跑完（8～15 分鐘），再確認線上版本真的換掉：

```bash
curl -s https://api.github.com/repos/MiaoZiKe/tw-rotation/actions/runs?per_page=3
```

如果這個容器的 egress 擋掉 `miaozike.github.io`（常常會），
**要誠實說「我打不開線上頁面，只能確認部署流程成功」**，不可以假裝驗過了。

### 6. 寫回報

格式固定成下面這四塊，順序不要換：

#### ① 網址與該看哪裡（永遠放最前面）

- 網址：<https://miaozike.github.io/tw-rotation/>
- **版號徽章**（右上角）應該是 `YYYY-MM-DD 第 N 版｜HH:MM`
- 我自己驗到什麼程度（誠實講，打不開就說打不開）

#### ② 任務表

| # | 需求 | 狀態 | 說明 |
|---|---|---|---|
| | 用 Andy 自己的話 | ✅ 完成 / 🔵 進行中 / ⬜ 未開始 / ⛔ 被擋住 | 完成的講「他打開網頁會看到什麼改變」；進行中的講**做到哪一步**；未開始的講**在等什麼** |

- ✅ 只給「已經 push 而且部署成功」的。改好沒推的是 🔵，不是 ✅。
- 🔵 一定要寫出**現在卡在哪一步**（例：關卡跑到第幾道、agent 還在跑哪一段）。
- ⛔ 一定要寫出**擋住它的是誰**（等 Andy 回答／等回補跑完／外部端點擋住）。

#### ③ 三道關卡的實際結果

紅字**逐條列出來**，每一條標明「是不是這一批造成的」。
既有紅字（例如容器 egress 擋 Yahoo 造成的個股即時分 K）要標「既有，不是這批」，
但**不可以因為它是既有的就不列**。

#### ④ 需要 Andy 決定的（只放真的擋住工作的）

「有重大問題再提問」—— 所以這一塊要克制：

- **能自己依證據判斷的就自己判斷**，不要拿來問他
- 只有「不同選擇會導致做出來的東西完全不同」才問
- 問的時候要把**選項、各自的代價、我的建議**一起給，不要只丟問題
- 沒有要問的就寫「沒有需要你決定的，可以直接休息」

## 紅線

- **一律繁體中文**，包含表格欄位名與狀態文字。
  例外只有程式碼、路徑、指令、公司原名、原始錯誤訊息。
- **不准把還沒 push 的東西標成完成。** 沒有 push 的工作等於沒做。
- **不准預測背景 agent 的結果。** 還在跑就寫「還在跑」，不要先寫它會做出什麼。
- **不准為了讓報告好看而省略紅字或已知限制。**
- 回報完如果還有背景工作在跑，要明講「還有什麼在跑、跑完我會再回報」。
