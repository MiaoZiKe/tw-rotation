# 科技透明圈 資料格式（site/tc/json/<產業id>.json）

一個產業一個檔，收集單位各寫自己的檔，前端只讀不改。

```json
{
  "industry": "foundry", "name": "IC 晶圓代工", "updated": "2026-10-25",
  "window": "2025-10-25～2026-10-25",
  "companies": [{
    "name": "台積電", "code": "2330", "heat": "Dcard 熱度：高／中／低",
    "benefits": "福利重點一句", "stock_plan": "員工認股／持股信託說明",
    "bonus_timing": "分紅發放月份", "culture": "風氣一句（評價摘要）",
    "interview": "面試流程一句",
    "roles": [{
      "unit": "單位（例：晶圓廠 Fab / 研發 R&D）", "role": "職位",
      "degree": "碩士", "years": "0-2",
      "base_month_k": [55, 65],      "bonus_months": [8, 12],
      "annual_months": [20, 26],     "annual_total_wan": [150, 200],
      "weekly_hours": 50, "overtime": "經常／偶爾／幾乎不",
      "travel": "需要／偶爾／不用", "n": 12,
      "note": "落差 1～2 萬疑為學士已排除等",
      "sources": [{"site": "GoodJob", "url": "...", "date": "2026-09"}],
      "confidence": "高／中／低"
    }]
  }]
}
```
規則：只收近一年（2025-10-25 後）、以碩士為主；數字一律區間；每筆至少一個來源；
GoodJob 為主、Dcard／PTT／其他做交叉比對，對不起來就寫進 note 並降信心度。
只寫「整理後的統計區間」，不轉貼原文、不放發文者帳號。

## mops 欄位（每家公司，2026-10-25 加，法遵：第一版以合法公開來源為主）

```json
"mops": {"year": "114年度", "avg_wan": 446.5, "median_wan": 355.2, "n": null,
         "source": "公開資訊觀測站 非擔任主管全時員工薪資（經媒體報導）", "url": "...", "note": "..."}
```
- 口徑：非擔任主管的全時員工薪資，排除經理人與部分工時；單位萬元／年。不可跟財報「全體員工薪酬」混用。
- 查不到填 null，note 寫查過什麼。`n` 為員工人數，報導沒寫就 null。
- 平台數字（GoodJob 為主，Dcard／PTT 交叉比對）可統計使用，不截圖、不轉貼原文；confidence 依筆數與交叉比對：≥2 筆且近一年＝中，≥5 筆＋兩平台吻合＝高，否則低。mops 當對照。

## 2026-10-25 補：職位表新欄與可見範圍
- 職位表欄位：學歷（`degree`）、底薪、分紅月數、年薪總月數（`annual_months`）、分紅發放（取公司層 `bonus_timing`）、年薪、工時、加班、出差（`travel`）。
- 新增選填欄 `degree_diff`（角色層，字串）：學士與碩士的差異，例「學士底薪約少 0.5～1 萬、分紅少 1～2 個月」；有填才在學歷欄下方顯示「學士：…」，沒填不顯示。
- 公司卡的底薪／分紅月數／年薪總月數是「符合篩選職位的最小～最大」，加班／出差取出現最多者；缺值一律顯示「—」。
- 可見範圍：只有管理者（`/v1/me` 的 `admin`／`owner`）看得到入口與頁面；其他人打 `#tc` 導回 `#overview`（見 tc.js `gate()`）。

## Andy 規則（2026-10-25）
原話：「只有台積電才有 ETE MAE 其他的只需要工程師；每間公司都有他對應的職等名稱，這也要分清楚，只有台積電比較特殊 大家不管學歷，但進去差別在就單位的繁忙程度，錢大部分都領的一樣」
1. MAE／ETE／技術員／IDL 等非工程師職位**只收台積電**；其他公司只收工程師職位（技術員列刪除）。
2. 公司層加 `grade_system`：該公司職等制度一句話（例：台積電 工程師職等 31/32/33…、經理 41…；聯發科 職級名稱…），查不到 null。
   職位層加 `grade`：該職位對應的公司職等名稱（例：「31 職等」「E1」），查不到 null。
3. 台積電：不分學歷（degree 寫「不限」），職位層加 `busyness`（單位繁忙程度：高／中／低＋一句依據），錢差異以單位繁忙度說明，不以學歷說明。其他公司照舊以碩士為主。

## 逐筆樣本（2026-10-25，Andy：「必須把樣本給上去，並且需要幫我做全部樣本統計，依產業、公司、單位、職位區分」）
職位層加 `samples`：每一篇文章／每一筆分享就是一筆，**n 必須等於 samples 的筆數**。
```json
"samples": [{"site":"Dcard","url":"https://www.dcard.tw/f/tech_job/p/...","date":"2026-05",
  "unit_detail":"Fab18 / 先進製程","years":"0-2","degree":"碩士",
  "base_k":65,"bonus_months":null,"annual_months":null,"annual_wan":220,
  "weekly_hours":55,"overtime":"經常","travel":"不用","quote_free_note":"自己的話摘要，不貼原文"}]
```
- 只記數字與短摘要，不貼原文、不放帳號。查不到的欄位 null。
- 職位層的區間（base_month_k、annual_total_wan…）由 samples 算出（最小～最大），不再手填。
- 前端：每個職位可展開看逐筆樣本；另有「樣本統計」頁，依產業→公司→單位→職位列筆數、底薪／年薪中位數與區間。

## 期間與主來源（2026-10-25 更新，Andy：「主要資料來自 Dcard……需要你去爬所有貼文，從 2025/08 至今」）
- 期間改為 **2025-08-01 起至今**；`in_window` 以 date ≥ 2025-08 判定。
- **Dcard 為樣本量主來源**（求職者、新鮮人 offer、面試提問），GoodJob 為精準度對照，PTT 補充。
- 做法仍是 WebSearch 限 dcard.tw 大量換關鍵字（公司×職位×薪水／offer／面試／分紅／年終），每篇一筆 samples；不登入、不用程式爬網站。
- **日期必須確認**（Andy：「所有資料獲取時務必確認他的日期，是否在我說的區間範圍內」）：每筆樣本加 `date_confirmed`（true＝摘要或標題裡看得到發文／分享日期；false＝推估）。
  只有 `date_confirmed:true` 且 date ≥ 2025-08 的樣本才進統計；推估日期的樣本列在逐筆清單但標「日期未確認」、不進統計。
  Dcard 以文章編號推估日期時，必須用同一輪查到、日期已確認的文章編號當錨點校準，並寫在 date_note；仍屬推估、不進統計。
- 日期判定細則（CEO 10-25 依證據拍板）：
  · PTT 文章代碼 `M.<Unix 時間>` 是發文時間本身 → 算確認（date_note 寫換算）。
  · 只寫年份：「2026」整年都在期間內 → 算確認；「2025」可能早於 8 月 → 不算確認。
  · GoodJob 標題附年月 → 算確認。
- 沒有任何已確認樣本的職位，區間一律 null（舊彙整值搬進 note「未逐筆對應的舊彙整：…」），不顯示成數字。
- Dcard 文章編號校準（docs/tc/dcard_id_calibration.md，32 個錨點、依日期單調遞增）：編號 ≥ 259537767 → `date_confirmed:true`（確認晚於 2025-08-01），date_note 註明依校準表。編號 259403174～259537766 仍算未確認。
