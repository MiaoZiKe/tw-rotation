## 3. 「限期限次體驗」規格（工程可照做）

### 3-1 名詞與跟「免費試用」的區隔（先講清楚，避免跟 10-09 決定打架）

- Andy 10-09 18:1x 決定**不提供免費試用**（＝不送「整個付費方案 N 天」），條款寫了「試用與退款保證合計一次」。
- 這次要做的是**「體驗額度」**：只給**被鎖住的付費功能**各 M 次、在期限內用完為止，**不改會員方案、不寫 `perm`、不建任何付款委託、到期不扣錢**。
- 所以：**體驗額度不算「免費試用」，用過體驗額度不影響 7 天退款保證**（我的判斷：體驗額度只是幾次看圖，不構成「白用一整期再退款」的濫用；把它算進去反而讓試用過的人不敢付費）。條款要加一條把這件事寫清楚（3-8）。前端文字一律用「體驗」「體驗次數」，**不准出現「免費試用」「1 個月／30 天」**（`_uitest` 已有斷言）。

### 3-2 兩種體驗

| 種類 | 誰拿到 | 期限 | 次數 | 例子 |
|---|---|---|---|---|
| `welcome` 新會員體驗 | 第一次 Google 登入（`users` 新建）的人，自動發 | 註冊起 N 天 | 每功能 M 次（期間合計） | N=7、M=3 |
| `promo` 上市體驗週 | 活動期間內所有登入的會員（含活動中才註冊的） | 固定起訖（`t0`～`t1`，1～2 週） | 每功能 M 次（期間合計，或每日 M 次，可設） | 10-13～10-26、M=5 |

N、M、哪些功能都是**管理區可改的設定**，不寫死在程式裡。

### 3-3 存在哪：account-api Worker（同一個 Durable Object SQLite）

照既有慣例在 `worker.js` **檔尾新增「體驗額度 grant 區塊」、包一層 prototype，既有函式一行不動**。

```sql
-- 活動／範本（管理者設定）
CREATE TABLE IF NOT EXISTS grant_defs (
  id TEXT PRIMARY KEY,          -- 'welcome' 或 'promo-202610'
  kind TEXT,                    -- 'welcome' | 'promo'
  name TEXT,                    -- 畫面顯示：「新會員體驗」「上市體驗週」
  feats TEXT,                   -- JSON {功能鍵: M}，例 {"flow.rot":5,"stock.page":5,"chain.diag":3}；功能鍵＝site/features.js 的 key
  per TEXT DEFAULT 'total',     -- 'total'（期間合計 M 次）| 'day'（每天 M 次）
  days INTEGER,                 -- welcome 用：註冊後幾天有效（N）
  t0 INTEGER, t1 INTEGER,       -- promo 用：起訖（毫秒，台北時間換算後存 UTC 毫秒）；welcome 也可用 t0/t1 限定「這段期間註冊的才送」
  audience TEXT DEFAULT 'free', -- 'free'（只給免費會員）| 'member'（所有登入者，付費者也拿但用不到）
  on_ INTEGER DEFAULT 1,        -- 開關
  updated INTEGER
);
-- 每個人拿到的體驗（發放紀錄）
CREATE TABLE IF NOT EXISTS grants (
  uid TEXT, gid TEXT,           -- gid → grant_defs.id
  start INTEGER, end_ INTEGER,  -- 這個人的生效起訖（welcome＝註冊時間＋N 天；promo＝活動 t0/t1）
  created INTEGER,
  PRIMARY KEY (uid, gid)
);
-- 用量（同 quota_hits 的「同一天同一單位只算一次」口徑）
CREATE TABLE IF NOT EXISTS grant_hits (
  uid TEXT, gid TEXT, k TEXT, day TEXT, key TEXT,
  PRIMARY KEY (uid, gid, k, day, key)
);
```

- 「一次」的定義**沿用 `quota_plan.md` 第 2 節**：同一天（台北日期）、同一單位（一檔個股＝代號；一個付費分頁＝功能鍵；一張剖析圖＝`c.<鏈>`）只算一次；今天看過的照樣能看。
- 剩餘次數**不存欄位、讀取時算**：`left(k) = M − COUNT(grant_hits WHERE uid, gid, k [AND day=今天 若 per='day'])`。不存「剩餘」就不會有扣錯、重複扣的問題。
- 為什麼不用「quota 系統另開一個方案範本」：範本是「一個人只有一個」（`perm.plan`），體驗要**疊在**原方案上、而且有期限與總量；做成範本就得改 `perm.plan` 再改回去，到期回退會跟付費訂閱搶同一個欄位。獨立表最乾淨。
- 保存：`grant_hits` 保留到 `end_` 後 30 天（客服查詢用），`grants`／`grant_defs` 保留 13 個月（跟反饋同口徑），刪帳號時一起刪（`deleteMe` 包裝裡加）。

### 3-4 API

| 端點 | 誰 | 輸入 | 回傳／行為 |
|---|---|---|---|
| `POST /v1/grants/me` | 已登入 | `{t}` | `{ grants:[{gid, name, kind, start, end, per, feats:{k:{max, used, left}}}], now }`；只回 `end_ > now` 的；**呼叫時順便補發**：符合條件的 promo 還沒有 `grants` 列就 INSERT（＝活動中第一次登入就拿到） |
| `POST /v1/grants/hit` | 已登入 | `{t, k, key}` | 規則見 3-5。回 `{ok:true, gid, left}` 或 `{over:true}`（這個功能沒有體驗可用了） |
| `POST /v1/admin/grants/defs/list` | 管理者 | — | 全部 `grant_defs`＋各自已發人數、已用次數 |
| `POST /v1/admin/grants/defs/put` | 管理者 | `{id, kind, name, feats, per, days, t0, t1, audience, on}` | 驗證：功能鍵要在 `V3_FEAT_K_RE`、M 為 1～999 整數、`t1>t0`、`days` 1～60；壞的整個 400（不存半套） |
| `POST /v1/admin/grants/defs/del` | 管理者 | `{id}` | 刪範本＝已發的 `grants` 一起失效（`grants`、`grant_hits` 保留給統計） |
| `POST /v1/admin/grants/user` | 管理者 | `{email}` | 客服用：查某人拿過哪些體驗、用了多少；可帶 `{extend_days}` 手動延長 |

**`welcome` 的發放點**：包 Google 登入回呼（新建 `users` 列那一步）。新建成功 → 檢查防濫用（3-7）→ 通過才 INSERT `grants(uid,'welcome',now,now+N天)`。**不在 `/v1/grants/me` 補發 welcome**（不然舊會員也拿得到）。

**`/v1/perm/me` 加一欄**：`grants: { k: left, ... }`（所有有效體驗合併後每個功能的剩餘次數），前端與 data-gw 都讀這一份，不用多一次往返。

### 3-5 權限判斷順序（跟付費訂閱同時存在時怎麼算）

對每一次「看某功能某單位」：

1. **站主／管理者** → 放行，不計。
2. **方案本身允許、而且沒有上限**（`feats[k]=true` 且 `lims[k]` 空、`dq` 空）→ 放行，**不扣體驗**（付費會員拿到 promo 也不會被扣）。
3. **方案允許但有每日上限**（例如註冊會員個股頁 10 次）→ 先吃方案的每日額度（`/v1/quota/hit` 既有邏輯）；**方案額度用完才吃體驗**（體驗＝加碼）。
4. **方案不允許**（`feats[k]=false`，被鎖住的付費功能）→ 看體驗：有 `left(k)>0` 的體驗 → 記一筆 `grant_hits`、放行；沒有 → 照舊蓋「需開通」卡（`qcard.js`）。
5. 同時有好幾份體驗（welcome＋promo）→ **先扣 `end_` 最早到期的那份**（讓先過期的不浪費）。
6. 全站共用額度 `quota.all`（`plans.dq`）：**體驗放行的那一次不算進 `quota.all`**（體驗是額外給的，不該吃掉他原本的每日額度）。

**付費訂閱期間**：體驗表照樣存在、照樣到期，只是第 2 步就放行了所以不扣。訂閱到期回到免費會員時，**體驗若還沒過期，剩餘次數照樣可用**。
**體驗跟帳務完全無關**：不寫 `perm`、不寫 `bill_flags.first_paid`、不設 `trial_used`，所以不影響 7 天退款保證（3-1）。

### 3-6 到期行為

- **讀取時判斷**（跟 `perm.expires` 同一招）：`end_ < now` 的 `grants` 一律視為不存在，不需要排程，不會漏。
- 到期後被鎖的功能恢復「需開通」卡；**已經看過的資料不追回**、自選清單等不受影響（體驗本來就沒碰這些）。
- 到期前 1 天：`notices` 發一則個人化提醒「體驗剩 1 天，還有 X 次」（`audience` 目前只到方案層級 → 第一版改成**前端看 `/v1/grants/me` 的 `end` 自己顯示提示列**，不靠 notices）。
- 促銷結束後，`grant_defs.on_` 不用手動關；`t1` 過了就自然失效。

### 3-7 防濫用

| 手法 | 擋法 | 強度 |
|---|---|---|
| 同一個 Google 帳號重複領 | `grants` 主鍵 `(uid, gid)`；`users.subh` 是 UNIQUE（Google `sub` 雜湊）→ 一個 Google 帳號只有一個 uid | 強 |
| **刪帳號再用同一信箱註冊** | 刪帳號時在 `benefit_hash` 寫 `kind='welcome'`（**沿用現有 HMAC 信箱比對碼與 365 天保存**，`billHash()`）；新註冊先查 `billHashKinds(email).has('welcome')` → 有就不發 | 強 |
| Gmail 別名（`a.b@gmail.com`、`ab+1@gmail.com` 其實是同一個信箱） | 算比對碼前正規化：gmail.com／googlemail.com 去掉「.」與「+」之後的字 | 中（只對 Gmail 有效） |
| 開很多個 Google 帳號 | **擋不乾淨**（Google 帳號免費）。緩解：①同 IP（以 `CF-Connecting-IP` 的 HMAC，不存原始 IP）每天發 welcome 上限 3 個，超過的照樣註冊但不送體驗 ②M 設小（每功能 3～5 次），讓開小號不划算 ③管理區「體驗用量」列出同一天註冊且用量滿的帳號，可用既有 `susp` 停權 | 中～弱；接受殘餘風險 |
| 前端改 localStorage 騙次數 | 次數只在 Worker 記（`grant_hits`），前端只顯示 | 強（對 account-api 管的功能） |
| 直接抓公開 JSON | **data-gw 沒部署前，被鎖的資料本來就在公開網址**——體驗額度只是畫面上的門。data-gw 上線後，data-gw 依 `/v1/perm/me` 的 `grants` 判斷，放行時打 account-api 內部端點記 `grant_hits`（同一把 `DATAGW_INTERNAL_KEY`） | 取決於 E12 |

隱私權政策要加一列：「為防止重複領取體驗額度，刪除帳號後保留信箱比對碼 1 年」（現在只寫了退款保證，範圍要擴充）；IP 只存 HMAC、保存 2 天。

### 3-8 條款要加的一條（草稿，法遵再看）

> **體驗額度**：本站得於特定期間或新會員註冊時，提供部分付費功能之有限次數體驗（「體驗額度」）。體驗額度之適用功能、次數與期間以活動頁或帳號頁所示為準，期滿或用罄即失效，不得轉讓、兌換現金或延長。體驗額度不屬於免費試用，使用體驗額度不影響退款保證之適用。以不正當方式（包括重複註冊）取得者，本站得取消其體驗額度。

### 3-9 前端

- 帳號選單與 `#pricing` 頂端：「上市體驗週：每項付費功能可體驗 5 次，到 10/26」＋「我的體驗」（各功能剩幾次）。
