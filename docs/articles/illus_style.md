## 0. 適用範圍與版本（先讀，否則會動到已上架的圖）

1. 現在的材質色全部是 CSS 變數（`--il-*`），**直接改值會讓已上架的 HBM、CPO、CoWoS 文章一起變色** —— 違反 Andy「這次先不改」。
2. 所以新規格以**版本旗標**上線：插圖 JSON 加 `"style": 2` 才吃新色票、新光影、新 detail；沒有 `style` 或 `style: 1` 一律照舊畫（原 CSS 與原畫法保留，不動一個像素）。
   - 建議做法：SVG 根節點加 class `ilv2`，新變數一律寫在 `.ilsvg.ilv2` 底下（深色）與 `:root[data-theme="light"] .ilsvg.ilv2`（淺色）。
3. 內建 kind（`cowos`、`rack`）也要支援 `style: 2`（換成新色票＋新光影），但舊文章沒帶旗標的不變。
4. `scripts/article_*` 自動產文串接完成後，**新文章的 illus 一律寫 `"style": 2`**（`production_guide.md` 的範例要同步改）。
5. 安全白名單照舊：新 mat、新 detail、新欄位都要進 `MATS`／`DETAILS` 白名單與 `cnum` 夾值；JSON 字串不得進 SVG。

## 1. 問題診斷：HBM 那張（`2026-10-17-know-hbm`）為什麼「不夠細緻、顏色太單一」

量測來源：`chk_illus_1440_light.png`、`chk_illus_1440_dark.png`、`chk_illus_390_light.png`（scratchpad/art_hbm/），插圖範圍逐像素統計（去掉卡片底色），色相以 30° 分組、彩度 < 0.15（HLS）算灰。

| # | 面向 | 量到的數字 | 為什麼是問題 |
|---|---|---|---|
| 1 | **色相集中** | 青綠（150°～210°）占有色面積 **淺色 45%／深色 44%**；米棕（30°）25%／14%；藍 17%；灰 9%／22%；其他色相合計 < 5% | 一個色相占近一半、前兩名合計約 **70%**，整張看起來只有「青綠＋米色」。 |
| 2 | **同材質重複當不同零件** | 8 個零件只用 6 種 mat；`si` 一色同時當「矽中介層」「HBM 底座」「右邊底層邏輯晶粒」**3 個零件**；`mem` 一色畫了 **5 塊**（HBM 疊＋4 片 DRAM） | 讀者分不出底層邏輯晶粒和中介層是不同東西，DRAM 與組好的 HBM 也同色。顏色沒有帶資訊。 |
| 3 | **明暗只有三階、而且是平塗** | 每個方塊只有頂／正／側三個平色（頂＝主色混 30% 白、側＝混 38% 黑），**沒有漸層、沒有高光、沒有倒角線、沒有接觸陰影**；整張插圖亮度只分布在 17～18 個 5% 區間 | 看起來像色塊模型，不像實物。 |
| 4 | **頂面被洗白** | 頂面混白後彩度掉 **19%～32%**（GPU 0.137→0.092、ABF 0.073→0.049）；淺色主題頂面對卡片底只有 **1.65～2.40:1**（矽 1.65、HBM 2.16） | 淺色主題下頂面幾乎融進底色，零件的「上緣」消失。 |
| 5 | **邊線太細** | 邊線 0.6（view 單位），1440 寬約 0.56px、390 寬約 0.32px（插圖縮放約 0.93／0.54） | 次像素邊線被抗鋸齒糊掉，相鄰零件只剩色差在分界。 |
| 6 | **細節密度不足** | 21 個積木裡，右邊 4 片 DRAM **0 個細節**；GPU 頂面格線只有 2 直 1 橫（3×2 格）；錫球半徑 2～3 → 1440 寬 1.9～2.8px、390 寬 **1.1～1.6px**，球的高光點在螢幕上看不到 | 「拆開看」的主角（DRAM 晶粒）是空白方塊；凸塊在手機上是灰點。 |
| 7 | **構圖空白** | view 600×360，積木外框只佔 y 162～342，**上方約 45% 是空的**；1440 寬實際圖形約 520×165px | 圖小、留白大，細節更看不到。 |

結論：問題不在「色盤裡色不夠」（現行 `--il-*` 兩兩 ΔE00 多在 16～41），而在 **① 一張圖可以只用兩三個 mat、② 同 mat 當不同零件、③ 平塗沒有光影、④ 細節沒有密度下限、⑤ 沒有構圖填滿規則**。以下五節逐一給下限。

## 2. 色彩

### 2.1 一張圖的配色配額（每張都要量）

| 規則 | 門檻 | 怎麼量 |
|---|---|---|
| 色相數 | 有彩度（OKLCH C ≥ 0.03）的面積，以 30° 分組，**占比 ≥ 5% 的組 ≥ 4 組** | `illus_audit`（見第 4.2 節）截圖逐像素統計 |
| 單一色相上限 | 最大的一組 **≤ 35%**；前兩組合計 **≤ 60%** | 同上 |
| 冷暖都要有 | 暖色（H 20°～110°）與冷色（H 180°～300°）各 **≥ 10%** | 同上 |
| 中性灰上限 | C < 0.03 的面積 **≤ 35%**（機殼類設備放寬到 ≤ 50%，例如機櫃） | 同上 |
| mat 數 | 零件數 ≥ 6 時，**不同 mat ≥ 5 種**；零件數 3～5 時 ≥ 3 種 | 讀 JSON |
| 同 mat 當不同零件 | **禁止**，除非用 `tone` 區分（見 2.5），且兩者 ΔE00 ≥ 8 | 讀 JSON＋算色 |
| 相鄰零件色差 | 互相接觸（外框相距 ≤ 2 view 單位）的兩個零件，正面色 **ΔE00 ≥ 15**；同一疊的層與層 ≥ 8 | `illus_audit` 讀 JSON 算 |
| 不螢光 | 所有填色 OKLCH **C ≤ 0.15**；深色主題填色 L ≤ 0.90（高光線除外）；**不准發光濾鏡、外光暈、`feGaussianBlur` 當光**；不准閃爍、脈動 | 讀 CSS／SVG |
| 紅綠語意 | 填色不得等於 `--rise`／`--fall`（ΔE00 ≥ 10）；`pcb` 綠與 `hot` 紅是材質色、可用 | 算色 |
| 對比 | 深色主題：正面對卡片底 ≥ 3:1，**不足的（深色材質）必須加 2.3 節的「輪廓光」**；淺色主題：正面 ≥ 3:1，**不足的（淺色材質）邊線必須 ≥ 3:1 且粗 ≥ 1.2 view 單位** | 表中已算好，新增色要自己算 |

### 2.2 三個面的明暗公式（box、cyl 都適用）

新色票全部由 OKLCH 推出來（可重算、可驗）；表 2.3 的 hex 就是用這組公式算的（超出色域時降彩度到可顯示）。

| 面 | 亮度 L | 彩度 C | 備註 |
|---|---|---|---|
| 頂面 | 正面 L **+0.09** | ×0.85 | 不再混白；頂面要保有材質色 |
| 正面 | 基準 L | 基準 C | 一律畫成**由上往下的線性漸層**：上 L+0.035 → 下 L−0.05（約 8 L* 的落差） |
| 側面 | 正面 L **−0.14** | ×0.95 | 側面再加一層由前往後 0 → −0.04 的漸層（遠處更暗） |
| 邊線 | 正面 L −0.30 | ×0.8 | 粗 **1.0 view 單位**（原 0.6）；`stroke-linejoin:round` |
| 高光線 | 正面 L +0.20 | ×0.45 | 只畫在「頂面與正面的交界」與「頂面與側面的交界」兩條稜線，粗 1.0、透明度 .85 |

量測：頂−正 ≥ 7 L*、正−側 ≥ 12 L*（CIELAB）。表 2.3 全部 27 種的最小落差：頂−正 8、正−側 16（深色）；頂−正 10、正−側 16（淺色）。

### 2.4 不可相鄰清單（ΔE00 < 12，不准放在互相接觸的位置）

以下組合色差不足，**不准相鄰**；如果結構上一定相鄰，其中一個要換 mat 或用 `tone` 拉開到 ΔE00 ≥ 15：

- 金屬灰族：`si`／`steel`／`magnet`／`tim` 兩兩之間；`steel`–`tray`（淺色）
- 黑族：`dark`／`rubber`／`mold`／`plastic` 兩兩之間；`tray`–`plastic`
- 藍族：`chip`／`battery`／`cold`（含淺色 `chip`–`tray`、`tray`–`battery`、`tray`–`cold`）
- 黃族：`fiber`／`gold`／`underfill`／`plate` 兩兩之間
- 其他：`cu`–`hot`、`solder`–`ceramic`

### 2.5 同材質不同零件：`tone` 欄位（新增）

`tone`：−2～+2 的整數，每一階正面 L ±0.05（頂、側、漸層跟著平移），C 不變。用途：同一種材料、但讀者要分得出的兩個零件（例如「組好的 HBM 疊」用 `mem tone:0`、「拆開的單片 DRAM」用 `mem tone:+1`）。兩者 ΔE00 必須 ≥ 8，否則改用不同 mat。**`tone` 不能拿來湊 2.1 節的色相數**（同色相不同明度仍算同一組）。

## 5. 分工流程（以後每篇文章的插圖）

自動產文時，同一輪排程依序派下面的角色；每一步交的檔放 `docs/articles/illus/<文章id>/`（草稿與審查紀錄進 repo；截圖放 scratchpad，不進 repo）。

| 步 | 誰 | 做什麼 | 交什麼檔 |
|---|---|---|---|
| 0 | 文章作者（產文的那一輪） | 文字定稿後，列出要畫的設備、要標的零件（id／名稱／一句話）、結構查證來源 | `brief.md`：零件清單＋來源＋「查不到所以只畫示意」的部分 |
| 1 | **動畫單位**（`animation-director` 主導，可派 `bibi-illustrator`／`storyboard-artist`） | 出構圖草稿：視角與 depth、哪些拆開／剖開、每個零件的 mat 與 tone、每個零件的 detail、配色配額試算（照 2.1 節，先用面積估） | `sketch.md`（零件表：part／type／mat／tone／detail／大約位置）＋`sketch.svg` 或 `sketch.png`（粗略方塊即可，標零件 id） |
| 2 | **網頁單位**（`tech-illustrator`） | 依草稿寫 illus JSON（帶 `"style": 2`）；需要新 detail／新 mat 時改 `site/artillus.js`；跑 `illus_audit` 與插圖驗收段落；截 4.1 節的 7 張圖 | 文章 JSON 的 illus 區塊、（有改的話）`site/artillus.js`、`illus_audit.json`、4.1 節截圖 |
| 3 | **審**：`animation-director`（細緻度、光影、配色配額、品牌一致）＋`art-director`（深淺主題、對比、不螢光）；結構有疑問加 `mechanical-engineer` | 照第 4 節逐條給過／不過 | `review.md`：每條過／不過、重疊檢查那行、並排圖檔名 |

## 6. 給網頁單位的實作順序（建議）

1. `artillus.js`：加 `style` 旗標與 `.ilv2` class；舊路徑完全不動（先截舊文章 HBM／CPO／CoWoS 深淺四張當基準，改完比對**像素一致**）。

## 附錄：色票推算方式

新色票由 OKLCH 參數（2.3 節第一張表）依 2.2 節公式推算，超出 sRGB 色域時每次降 C 0.002 直到可顯示；ΔE00 用 CIEDE2000、對比用 WCAG 相對亮度。卡片底色取自實際截圖：深色 `#0F1C2F`、淺色 `#F1F6FA`。新增 mat 時照同一套公式算，並補驗 2.1 節的對比與 2.4 節的不可相鄰清單。
