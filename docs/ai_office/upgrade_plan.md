# AI Office 角色美術與物理動畫升級：實作規劃（2026-11-13）

依據：`upgrade_diagnosis.md`（診斷與量測）＋擁有者要求第一～十一節。
**原則：先讓一隻（糰糰）到 90 分，再動其餘。** 優先順序照擁有者第十一節：P0 → P1 → P2。
本文的數字有三種：**實測**（標明量法）、**推算**（由程式碼或公式算出）、**提案**（我建議的起始值，要靠美術驗收調）。

## 一、技術選型（結論＋實測）

### 擁有者點名的突破
「高品質參數化角色曲面＋骨架／Morph Target 動畫，而不是增加更多物件與動作名稱。」

**落地方式（結論）：兩段式分工**

1. **離線（Blender Python，bpy 5.3.0）**：用參數化腳本一次產出每個物種的「一體成形網格＋骨架＋蒙皮權重＋形態鍵＋頂點色 AO＋三級 LOD」，輸出 GLB 提交進 repo。腳本是參數化的（橢球清單＋骨架清單＋形態鍵清單），不是手工雕刻，所以可重現、可批次、可調整。
2. **執行期（three.js r160，現有 vendor）**：`GLTFLoader` 載入 → `SkinnedMesh`（GPU 蒙皮＋形態鍵）。**材質、臉、物理、動畫控制器、卡通變形、次級擺動全部留在 JS**（沿用 `softMat` 的圖樣／戳凹陷／上下漸層／個體差異，改掉假 SSS 與邊緣光）。GLB 只提供「網格＋骨架＋形態鍵＋AO」，**動作不烘進 GLB 的動畫片段**（因為動作要與物理分層、要受個性與接觸控制，用程式驅動骨頭）。
3. **備援**：純程式的距離場路線（見下表）已實測可行；若未來某個 session 裝不起 bpy，可用它產出同樣用途的網格，或做執行期個體變形。

**為什麼不是只選 (a)**：形態鍵與骨架權重是擁有者點名的關鍵，而 Blender 這兩樣是成熟工具；且 (a) 的不規則三角形對蒙皮與形態鍵（要在同拓樸上變形）不友善。
**為什麼不是只選 (b)**：不依賴 Blender 的備援要保留；個體差異大幅變形（例如寵物版本）用執行期骨頭縮放解決，不重生成網格。
**不建議**：GPU 距離場即時生成、行進立方體在執行期每幀跑（現有 `character_factory.md` 第七節已記錄不採用的理由，仍成立）；Draco／meshopt 壓縮（沒有解碼器）。

## 二、動畫控制器與狀態機設計

### 分層（解決診斷 4.1、4.2、9：誰擁有哪個通道）

| 層 | 負責 | 擁有的通道（只有它能寫） | 備註 |
|---|---|---|---|
| L0 物理 | 位置、速度、接地、碰撞、重力、拋擲 | `root.position`、`root.yaw`、`vel`、接觸資訊 | 固定步進 1/120 s（累加器＋視覺插值），`step` 內建，呼叫端不必切子步 |
| L1 卡通變形 | 擠壓伸展、斜切、果凍晃、呼吸 | `visual` 骨的縮放與斜切 | **只作用在 visual 節點**；以接觸點為樞紐；體積守恆；被限制（見下）。**不影響物理位置** |
| L2 骨架姿態 | 走／跑／跳／坐／摸／情緒姿勢 | 骨頭旋轉：身體、頭、手、腳、耳、尾 | 動作資料化（五段）＋腳 IK＋次級彈簧 |
| L3 臉 | 眼球、眼皮、嘴形態鍵、貼花 | `eye.*`、形態鍵權重、貼花參數 | 表情＝資料；視線追蹤獨立 |
| L4 附屬 | 道具、配件、頭上圖示、粒子、音效事件 | 不寫角色 transform | 只讀骨頭世界矩陣 |

**單一寫入者規則**：`TransformBus` 在 QA 模式（與測試）裡記錄每個通道每幀被誰寫了幾次，**超過一次且來源層不同＝錯誤**。

### 每個動作的五段結構（資料表示）

```js
// 每個動作一筆資料，控制器直譯；時間單位秒，曲線＝命名 easing
{ name: 'jump',
  start:  { pose: 'idle' },                             // 1 起始姿態：由目前姿勢混入（不瞬移）
  pre:    { dur: 0.12, squash: -0.22, lean: -0.06, ease: 'inCubic' },   // 2 預備（蹲）
  main:   { until: 'leaveGround', stretch: +0.16, tuck: 0.4 },          // 3 主動作（由物理事件結束）
  settle: { dur: 0.45, from: 'landImpact', spring: { hz: 3.2, zeta: 0.35 } }, // 4 緩衝與收尾（彈簧）
  out:    { to: 'idle', dur: 0.2, blend: 'cross' },                    // 5 返回待機（可中斷）
  interrupt: ['grab', 'poke'], events: [{ t: 'pre.end', sfx: 'jump' }, { t: 'land', fx: 'dust' }] }
```
辦公室一次型動作（`nod／wave／clap…` 共 13 個）也照此表：預備 80～150 ms、主動作、收尾 150～300 ms、回待機。**驗收＝動作結束後骨頭姿態與待機差 ≤ 容許值（自動測試）**。

### 卡通變形與物理運動怎麼分層

- 物理（L0）決定**質心的位置與速度**與**接觸事件**。
- 卡通（L1）只改 `visual` 節點的縮放／斜切，**以接觸面為樞紐**（腳底平面或坐面），所以永遠不會往地面以下長。
- **限制（規則 10）**：每幀由控制器算 `sy` 與 `sx = 1/√sy`（體積守恆），然後夾限：頭頂 ≤ 天花板／桌底（`env.clearance`）；水平半徑 ≤ 與最近牆／家具的距離（碰撞形狀擴張後仍不穿）；`sy ∈ [0.62, 1.30]`；超過就降振幅而不是穿透。
- 傾斜樞紐：移到身體重心，並以「最低接觸點」重新貼地，避免一側下沉（診斷 8.2）。

### 次級動作
耳朵（2 節）、尾巴（2 節）、手臂：每節一個阻尼角彈簧，輸入是**身體加速度與角速度**（延續現有 `apps` 的做法，診斷 2.4），參數放個性檔；同一組固定步進。

## 四、臉部控制（Facial Rig v2）

## 五、材質預設六種（Material Preset）

底層：Standard 為預設，**近景（LOD0 且螢幕佔比大）才用 Physical**（`sheen／clearcoat`）；遠景全部 Standard。環境光：沒有 HDR 檔（離線環境、不引入 CDN），用 `PMREMGenerator`（three 核心內建）從一個小的漸層場景生成**程序化環境貼圖**（暖白天空＋暖地面＋一條亮帶），強度 0.35，只供高光反射；柔和 AO 來自頂點色。不使用 `RoomEnvironment`（vendor 沒有，且太亮太冷）。
**通則（防「過度反光、油膩」）**：非陶瓷 `roughness ≥ 0.45`；`clearcoat ≤ 0.2`（陶瓷 ≤ 0.6）；`envMapIntensity ≤ 0.5`；SSS 與邊緣光改為**受光照調變**並設上限（SSS ≤ 0.18、rim ≤ 0.12），不再直接加進 emissive（診斷 3.1）。

| 預設 | 適用 | roughness | metalness | 其他參數（提案） | 近景額外 | 遠景退化 |
|---|---|---|---|---|---|---|
| 軟綿絨毛 | 糰糰、倉鼠、兔、水豚 | 0.88 | 0 | 頂點色 AO 0.55；rim 0.10；法線擾動（絨毛微紋理，貼圖 64²）| `sheen 0.7、sheenRoughness 0.6、sheenColor` 淡暖白 | 取消 sheen |
| 柔霧塑膠 | 收藏公仔感（糰糰預設可選）、機器人、杯子 | 0.55 | 0 | AO 0.5；specularIntensity 0.5 | `clearcoat 0.15、clearcoatRoughness 0.5` | 取消 clearcoat |
| 半透明果凍 | 布丁、史萊姆、幽靈 | 0.30 | 0 | alpha 0.9、fresnel 邊緣略亮（≤0.12）、內層深色漸層偽 SSS | `transmission 0.25、thickness 0.5、ior 1.35`（有 transmission 的 Physical 會多一次不透明場景渲染，**辦公室不開**） | 只留偽 SSS＋alpha |
| 陶瓷 | 杯子、印章、公仔 | 0.28 | 0 | AO 0.4；envMapIntensity 0.45 | `clearcoat 0.6、clearcoatRoughness 0.12` | clearcoat 0.3 以 Standard 的 roughness 0.2 取代 |
| 橡膠 | 腳掌、輪胎感、手套 | 0.72 | 0 | specularIntensity 0.3；AO 0.5 | `sheen 0.15` | 同 |
| 柔軟雲朵 | 雲、棉花、泡泡 | 1.0 | 0 | 邊緣包覆光（wrap lighting）0.25；emissive ≤ 0.03（**不發光**）；AO 0.3 | `sheen 1.0、sheenColor` 白 | 取消 sheen |

驗收：每個預設用同一顆球＋同一組燈在深／淺背景各截一張，**由人工看**「不油、不爆白、材質感可分辨」。

## 九、風險與對策

| 風險 | 對策 |

## 十、需要拍板或確認的事（我不擅自決定）

1. **糰糰的定位**：程式裡 `mochi`＝麻糬糰子（圓耳、短尾），擁有者原話稱「奶油倉鼠」。本規劃以現有糰糰（奶油色麻糬團子）為準，不加倉鼠特徵。**若要倉鼠（頰囊、倉鼠耳形），第二階段建模前請告訴我。**
2. **「麻糬精靈」與糰糰的差異**：第十節的麻糬精靈（無複雜四肢、練柔體）與現有糰糰（有四個凸起肢）重疊。規劃把糰糰當第一隻，**麻糬精靈放第六階段第一批，定位為「無肢柔體版」**；若擁有者認為「麻糬精靈＝糰糰」，第六階段可省一隻。
3. **小海豹＝滾滾升級**（擁有者說「現有滾滾可直接升級」）：照辦，不新增。
4. 步頻（現在單腳 3.7 Hz 的小碎步 → 提案 2.1 Hz）是美術取向，第三階段做出來後由人工驗收決定。
