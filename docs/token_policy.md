# 全公司 Token 政策（2026-10-19 第 1 版）

> Andy 10-19 原話：「CEO 幫我派人優化 Token 使用，盡量以 CP 最高方式進行，但需要控制 Token 使用」「這是每個單位都需要做的事情」。
> 負責單位：`resource-auditor`（資源稽核）。適用：CEO、`.claude/agents/` 全部單位、所有排程（精選文章、社群部、主題生成、tts 等）。
> 紅線不變：**不准為了省 Token 少驗收、少讀關鍵檔案、或用估的數字代替查證**；精選文章品質門檻 75 分不准降。砍的是重複與無效的花費。

## 二、模型分級（照表做，不用想）

| 工作長什麼樣 | 模型 | 例子 |
|---|---|---|
| 查檔、普查、列清單、讀狀態檔、數東西 | **haiku** | 「哪些檔用到 X」「列出 agents 的 frontmatter」「資料新不新」「把截圖縮圖」 |
| 格式轉換、搬資料、照範本填表 | **haiku** | JSON ↔ 表格、逐格 GIF／WebP 輸出、評分紀錄 JSON、改日期 |
| 簡單文件（照既有格式補一段、改錯字、更新索引） | **haiku** | 補 `features.json` 一則、更新 HANDOFF 勾選 |
| 撰寫（文章、文案、腳本、分鏡、查證報告） | **sonnet** | 精選文章撰寫、社群週包、三位鏈別分析師 |
| 一般前端改動、手機樣式、單一頁面互動 | **sonnet** | frontend-ui、mobile-ui、canvas-motion-engineer |
| 測試修正、驗收段落補寫、部署 | **sonnet** | deployer、補 `uitest_sections/*.py` |
| CEO 審稿、最終驗收、監察 | **opus** | reviewer、inspector、排程對話裡的審稿 |
| 跨檔架構（≥ 3 個大檔一起改、資料口徑、共用工具） | **opus** | 改 `build_payload.py` 輸出格式、`app.js` 共用工具 |
| 金融口徑、指標算法、法遵、資安判斷 | **opus** | finance-quant、smc-technical、legal-compliance、security-privacy |

- **單位定義檔寫的是預設**；CEO 派工時用 Agent 工具的 `model` 參數可以**升一級**（例如 sonnet 單位碰到跨檔架構就帶 `model: "opus"`），派工單要寫理由。降級不用理由。
- haiku 做錯一次 → 同一件改 sonnet 重做，不准讓 haiku 重試第二次。
- **Explore／general-purpose 普查一律帶 `model: "haiku"`。**

## 三、每類任務的預算上限

| 任務 | 目標 | 上限 | 備註 |
|---|---|---|---|
| 普查／查檔（haiku） | 3 萬 | 6 萬 | 交件 ≤ 15 行 |
| 部署（deployer） | 3 萬 | 6 萬 | 測試背景跑 |
| 查證報告（鏈別分析師、市場研調） | 10 萬 | 15 萬 | WebSearch ≤ 12 次 |
| 精選文章撰寫 | 17 萬 | 20 萬 | 一篇合計上限 35 萬（`fast_path.md`） |
| 主題生成 | 5 萬 | 8 萬 | WebSearch ≤ 6 次 |
| 社群部每週包（7 則） | 30 萬 | 45 萬 | 見章程第八節 |
| 一般前端改動（單頁、單功能） | 15 萬 | 25 萬 | |
| 大型前端改動（跨頁、新元件） | 25 萬 | 35 萬 | 超過就拆兩件，各自上線 |
| 動畫、插圖（新種類） | 20 萬 | 30 萬 | 套現成積木 ≤ 5 萬 |
| 審核（reviewer）／監察（inspector） | 8 萬 | 15 萬 | 只看交件與 diff，不重做普查 |
| 法遵／資安審查 | 8 萬 | 12 萬 | |
| 金融口徑、指標 | 15 萬 | 25 萬 | |

**超支處理（三步，照順序）**：
1. **到目標的 1.5 倍或上限其中先到的那個 → 先停**，不再開新的讀檔或測試。
2. **回報**：做到哪、還差什麼、為什麼超（讀了哪個大檔／重跑了幾次）、剩下的估多少。
3. **拆小**：CEO 把剩下的拆成一件或兩件新派工（各自有預算），不准讓原 agent 直接「再給我 10 萬」。

## 四、省 Token 的硬規則（每條都能量）

| # | 規則 | 怎麼量 |
|---|---|---|
| 1 | **大檔不整份讀**：一-3 表裡的檔一律 `grep -n` 定位，`sed -n 'a,bp'` 或 Read 帶 offset／limit，每次 ≤ 200 行 | 逐字紀錄裡對這些檔的 Read 沒帶 limit ＝ 違規 |
| 2 | **工具輸出要收窄**：`git log --oneline -n 20`、`| head`、`--name-only`、API 帶 `per_page`、Python 只印要的欄位 | 單次工具輸出 > 1 萬字元 ＝ 違規（除非就是要那份內容） |
| 3 | **驗收只跑對應段落**（`--sections`／`--module`），推 main 前才加桌機守門；完整一輪只在 Andy 說「全部驗一次」 | 回報要寫「驗了哪幾段」 |
| 4 | **測試一律 `run_in_background`，跑完才醒**；不 tail、不 sleep 輪詢 | 快取寫入 > 5 萬的回合數／agent ≤ 2 |
| 5 | **截圖只截必要張數**：預設 2 張（1440、390）；要細節用 `--sel` 截那一塊；傳給 CEO 前縮到寬 ≤ 1200px | 一件交件 ≤ 4 張圖（並排比對圖算 1 張） |
| 6 | **回報上限**：子 agent 交件 ≤ 12 行；CEO 回 Andy 照 report-progress 格式，不灌細節 | 數行數 |
| 7 | **重用既有**：先 `grep` 有沒有現成函式、段落、積木、範本（`site/modules.js`、`scripts/uitest_sections/`、插圖積木）再寫新的 | 審核時看 diff 有沒有重複實作 |
| 8 | **不重複普查**：同一題 24 小時內普查過，結果存在 scratchpad 或 `docs/`，下一個 agent 讀結果不重查；派工單附上前一次的路徑 | CEO 派工單有「已知事實」欄 |
| 9 | **交件格式固定**（第五節範本），不准附整份程式碼或整份 log | — |
| 10 | **失敗最多重試 1 次**：同一指令／同一段驗收紅兩次就停，換做法或記「待處理」 | 同指令連跑 ≥ 3 次 ＝ 違規 |
| 11 | **平行上限**：同時最多 3 個寫程式的 agent、3 組測試（`run_gate.sh`）、2 個文章撰寫 agent；普查類 haiku 不限但 ≤ 5 | — |
| 12 | **開工先讀 `HANDOFF.md` 的「下一步」與 `DECISIONS.md` 相關條目（grep）**，已經寫過的不重查 | — |
| 13 | **一件事一個人**：不派兩個 agent 做同一件、不讓監督重做一次普查 | — |
| 14 | `site/data` 用 symlink，不准複製進 worktree | — |

## 五、CEO 派工模板（每一張派工單都照這個）

```
【任務】一句話，用 Andy 的話
【單位／模型】<agent 名>／<haiku|sonnet|opus>（升級要寫理由：＿＿）
【預算】目標 ＿ 萬、上限 ＿ 萬（照第三節）；到 1.5 倍先停回報
【已知事實】前一次普查／決策的路徑（沒有就寫「無」），不要重查
【要讀的檔】只列必要的；大檔寫「grep 關鍵字 X，讀該段」
【不准動】＿＿（例如 site/、workflows）
【驗收】跑哪幾段（--sections …）＋桌機守門與否；截圖幾張、哪兩個寬度
【交件（≤ 12 行）】改了哪些檔、commit、驗了哪幾段結果、截圖路徑、
                   實際花了多少 Token（subagent 回報的用量）、沒做完／不確定的
```

## 六、每週量測（誰、在哪看、超標怎麼調）

- **負責人**：`resource-auditor`，**每週一**（排在上週社群包交出之後）做一次，產出 `docs/token_weekly/<週一日期>.md`（≤ 40 行）。CEO 派它，模型 sonnet，預算上限 8 萬。
- **看哪裡**：
  1. **排程**：用 `list_triggers` 拿各排程最近的 run，`list_events`（`kinds:["result"]`）讀每輪的 `total_cost_usd` 與 Token 用量；分成「空跑」「有做事」兩類算平均。
  2. **子 agent**：每張交件單的「實際花了多少 Token」欄（Agent 工具結果的用量），CEO 每批記一行到 `docs/token_weekly/` 當週檔的「派工帳」。
  3. **逐字紀錄**（需要深挖時）：照 `docs/efficiency_1010.md` 的方法算快取寫入 > 5 萬的回合數。
- **報告格式**：`項目｜現在花多少｜省下多少｜怎麼省｜會不會影響正確性`，只列前 5 名。
- **超標怎麼調**：
  - 某類任務連兩週平均 > 上限 → 拆小或改派工範本（寫進本檔第三節，附原因）。
  - 某單位 haiku／sonnet 交件被退 ≥ 2 次／週 → 該單位升一級，記在本檔 1-1。
  - opus 單位連四週沒有需要 opus 的判斷 → 提案降級，CEO 決定。
  - 文章品質：平均分 < 75 時**不准用加 Token 解決以外的方式降標準**；先看是哪一項扣分，再決定加在哪。

## 七、給 CEO 的排程提示詞重點（排程由 CEO 改，本單位不動排程）

2. **撰寫 agent** 一律帶 `model: "sonnet"`（已寫在 fast_path），**審稿留在排程對話本身**（opus）。
3. **社群部週日**：提示詞寫明「growth_plan 只讀第九、十二節（grep 標題取行號）」「7 則用一個 sonnet agent 一次寫完，不要一則一個 agent」「預算上限 45 萬」。

5. **所有排程**：提示詞結尾加「交件附本輪用量一行」，給每週量測用。
