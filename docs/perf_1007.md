# 開頁速度量測與優化（2026-10-07）

Andy 原話：「開啟網頁再入速度太慢，幫我優化」。

## 量法

- 本機 Playwright（Chromium），`#overview`，視窗 1440×900。
- 網路模擬 Fast 3G：延遲 562.5ms、下行 180KB/s、上行 84KB/s；CPU 降速 4 倍。
- 本機伺服器**開 gzip**（模擬 GitHub Pages 的壓縮傳輸），`Cache-Control: max-age=600`。
- 「首次」＝全新瀏覽器設定檔；「第二次」＝同一個設定檔先到 about:blank 再開（吃 HTTP 快取＋開頁存檔）。
- 「首屏圖表畫完」＝頁面上出現第 3 個 canvas 的時間（從 goto 起算）。
- ⚠ 容器裡同時有其他 agent 在跑瀏覽器，單次量測誤差約 ±0.5～1 秒；FCP 的落差遠大於誤差。
- 量測腳本放在 scratchpad（不進 repo）；未開 gzip 時首次 FCP 為 20.5 秒、總量 7.2MB，那是本機伺服器不壓縮造成的，不代表線上。

## 做了的

1. **echarts／lightweight-charts／timegrid 從 `<head>` 搬到 `<body>` 底部（drawtools.js 之前）**。
   執行順序不變（仍在 chart.js、app.js 之前），只是瀏覽器不必先下載完約 400KB 才畫頁框。
   效益：首次 FCP 7.1 → 2.9 秒（-4.2 秒）。代價：無（同步腳本照順序執行）。

## 試過、撤回的

2. **etf.json 延後到 load＋閒置才抓**（省首屏 184KB 頻寬，首屏圖表約 -0.7 秒）。
   `_uitest --sections 新-開頁存檔` 單獨跑就穩定變紅（第二次開頁 1 秒內大盤三張圖 0 張），
   原版與「只有第 1 項」都綠，所以確定是這一項造成。依「追根因最多 10 分鐘」撤回，沒上。
   推測是開頁存檔的寫入時機跟「所有 load() 都結束」有關，延後的 etf 讓存檔沒寫完整 —— 未證實。

## 沒做的（建議順位）

| 項目 | 估計效益 | 代價／風險 | 為什麼這次不做 |
|---|---|---|---|
| 開站 `L.init` 不等 industry_map＋supply_chain（200KB）就先 route 總覽 | 首屏圖表約 -1.5～2 秒 | 全站共用的 `L.*` 對照表會晚到，搜尋、族群名稱都依賴它 | 動到全站初始化順序，要先盤點誰讀 `L.ready` |

| echarts 換成按需精簡版 | -150～200KB | 要列出全站用到的圖種，漏一種就整張空白；容器沒有 npm 來源可建置 | 風險高、本機無法建置 |
| 桌機不載 mobile3.js（162KB 原始／約 50KB gzip） | 約 -0.3 秒 | 視窗縮到 ≤640 時要能補載 | 效益小 |
