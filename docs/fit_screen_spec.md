# 一屏看完規格（2026-10-03，設計美編，分支 `claude/fit-screen`，DECISIONS #308）

接續 `docs/ui_polish_spec.md`（第一版精修規格）。這份只處理一件事：**每張圖表卡的高度**。

Andy 原話：「版面上下太大，希望是一個電腦螢幕大小可看到完整圖表，幫我上下寬度調整窄一點適當」
（附圖：資金去向桑基樹高到要捲好幾屏、資金輪盤圓盤很大、右邊排行很長）。

## 0. 量法與依據（誠實交代）

- **沒有競品截圖**：這份不是對標，是對「Andy 的附圖」＋「我們自己的頁面」量。依據欄寫的「量自」＝在 Playwright（Chromium）
  真圖表庫下，用 `getBoundingClientRect()` 量每張可見 `.card` 的高度（DOM 量測，不是截圖數像素；腳本在 `_uitest.py` 的
  `FIT1003_CARDS`，改前改後用同一支）。
- **視窗尺寸**：規格的「可視高」是瀏覽器扣掉網址列與書籤列之後的內容區：1920×1080 螢幕 ≈ 950、1440×900 螢幕 ≈ 800。
  下表的「改前／改後」量的是 **1920×950 與 1440×800**（對應真實瀏覽器），驗收腳本另外在 1440×900、1920×1080 原始視窗驗一次。
- **「一屏」的定義**：卡高 ≤ 視窗可視高 − 49（黏在頂端的本頁功能跳轉列 `#l4Jump`，32 按鈕＋上下內距 8×2＋1 框線）。
  CSS／JS 取的上限 `Fit.cap()` ＝ 視窗高 − 49 − 24（卡的上下各留 12px 邊距），比「一屏」再嚴 24px。
- **只動高度與間距**：不改功能、id、`data-*`、配色、路由、側欄；手機（≤820）一個 px 不動。

## 6. 資金去向再縮小（2026-10-03，DECISIONS #313，分支 `claude/sankey-fit`；接續 #308）

Andy：「資金去向，還是無法打開來就看全部，需要再縮小點」。目標：**一打開（不捲動、不點展開）整棵樹的每個節點與標籤都在可視範圍內**，
1440×900（可視高約 800）、1920×1080（約 950）都成立，1366×768（約 650）盡量。

### 6.1 量法（誠實交代）
- Playwright Chromium、真圖表庫、`#flow/sankey`，等 3.5 秒讓卡高收斂；用 `FlowTopo.probe` 取每個節點標籤的外框（`lab`）＋畫布在視窗的位置，
  再量「在不在 0..視窗高 內」「兩兩是否重疊」。**量的是這台容器的字型**（`/opt/pw-browsers/chromium`）；標籤高度固定 17px、字級 12px 與字型無關，字寬會因字型差幾 px。
- 螢幕解析度不等於可視高：瀏覽器工具列＋分頁列約吃 100～120px，所以除了 1440×900／1920×1080／1366×768 之外，另量 800／950／660，
  以及 Windows 縮放 125%（1152×640）與 150%（1280×600）時的 CSS 視窗。
- 資料：2026-10-02 最新 `sankey_daily`，18 個族群、5 條產業鏈（本機 `SKIP_INTRADAY=1 python -m pipeline.build_payload` 重算）。

### 6.4 沒做「兩欄」的理由
Andy 的備案是「仍放不下就改兩欄」。以現有資料（18 族群、5 鏈，槽數 20）槽高 18 時畫布只要 384px，**到可視高約 553 都放得下**（再矮是 `Fit.cap()` 的全站下限 480，不是槽高），兩欄的條件沒有成立。
限制寫明：若族群增加到 28 個（槽數約 30），槽高 18 要畫布 564px，可視高 < 約 700 時會超出一屏；到時再做兩欄（每條鏈的族群分左右兩群、`layoutClassic` 的 `cols` 多一欄）。
