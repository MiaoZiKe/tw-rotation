# 一屏看完規格（2026-10-03，設計美編，分支 `claude/fit-screen`，DECISIONS #308）

接續 `docs/ui_polish_spec.md`（第一版精修規格）。這份只處理一件事：**每張圖表卡的高度**。

Andy 原話：「版面上下太大，希望是一個電腦螢幕大小可看到完整圖表，幫我上下寬度調整窄一點適當」
（附圖：資金去向桑基樹高到要捲好幾屏、資金輪盤圓盤很大、右邊排行很長）。

## 0. 量法與依據（誠實交代）

- **沒有競品截圖**：這份不是對標，是對「Andy 的附圖」＋「我們自己的頁面」量。依據欄寫的「量自」＝在 Playwright（Chromium）
  真圖表庫下，用 `getBoundingClientRect()` 量每張可見 `.card` 的高度（DOM 量測，不是截圖數像素；腳本在 `_uitest.py` 的
  `FIT1003_CARDS`，改前改後用同一支）。
- **視窗尺寸**：規格的「可視高」是瀏覽器扣掉網址列與書籤列之後的內容區：1920×1080 螢幕 ≈ 950、1440×900 螢幕 ≈ 800。
  下表的「改前／改後」量的是 **1920×950 與 1440×800**（對應真實瀏覽器），驗收腳本另外在 1440×900、1920×1080 原始視窗驗一次。
- **「一屏」的定義**：卡高 ≤ 視窗可視高 − 49（黏在頂端的本頁功能跳轉列 `#l4Jump`，32 按鈕＋上下內距 8×2＋1 框線）。
  CSS／JS 取的上限 `Fit.cap()` ＝ 視窗高 − 49 − 24（卡的上下各留 12px 邊距），比「一屏」再嚴 24px。
- **只動高度與間距**：不改功能、id、`data-*`、配色、路由、側欄；手機（≤820）一個 px 不動。

## 2. 與 `ui_polish_spec.md` 衝突之處（為什麼改）

- §（熱力圖格高 28px，約 line 430）：**12px 字級下限與 28px 格高照舊**；只在「整張卡超過一屏」時列高往下縮，下限 20（格高 16 仍放得下 12px 數字）。
  20 列、視窗可視 800 時量到 28 → 27。
- 「資金輪盤與桑基上下疊」（總覽）：改為卡內左右。理由＝疊起來比一屏高；桑基本來就有窄版排法。
- 桑基族群槽高下限 36 → 22：36 是為了「代表股三檔一欄每檔 13px 不疊字」；預設收起時代表股畫在另一欄、一次只一個族群，
  不會跟鄰格疊字。**點開展開（`extra > 0`）時照舊允許長高**，所以資訊沒有消失，藏起來有入口。

## 3. 驗收

- `_uitest.py` 新段落 `一屏看完1003`：1440×900 與 1920×1080 各逐頁（總覽、資金流向三子分頁、熱力圖兩子分頁、產業地圖、
  市場明細、週期統計、自選、個股＋十個分頁）量每張可見卡 ≤ 視窗高 − 49、頁面沒有橫向捲軸；視窗 1000 → 700／800 縮矮，
  資金去向、輪動、個股 K 線卡跟著縮；1920×1080 K 線本體 ≥ 560、輪盤 ≥ 500（沒被過度壓縮）；390 手機沒有橫向捲軸。
- 反向驗證：把 `Fit.cap()` 改成永遠回 99999 → 該段 4 條紅（資金去向 1003、總覽輪盤卡 1148、兩條不跟著縮）；還原後 0。

## 4. 設計取捨與已知限制

- 個股 K 線本體下限 420：視窗可視高 < 約 770 時（例如 1366×768 筆電）個股 K 線卡仍會超出一屏，再壓副圖與價格軸會擠在一起。
- 輪盤的左右是方的：高縮了、寬不變，盤在欄裡置中、兩旁多出空白（1440×800 時輪動卡盤面約 515px）。
- 月營收明細：台積電這種九位數「累計營收」的表在 1440 仍會表內橫捲、年／月欄釘左（`index.html` 既有註解已寫明）。
- 沒驗到：點開才出現的東西（資金去向展開族群、放大面板、說明浮層）；淺色主題只驗了既有 `淺色主題` 段落的初始畫面。
