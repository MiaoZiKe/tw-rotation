## 2. 月曆 UI

### 2.1 入口

| 位置 | 做法 | 備註 |
|---|---|---|
| 桌機頂欄右側、帳號區左邊 | 高 32 的圖示鈕（月曆＋勾），圓角 `--r-sm`；今天還沒簽到時右上角有一個小圓點，簽完消失 | 比照 `andy_ui_rules` C9；不彈窗打擾 |
| 總覽頁摘要卡列的**第一張** | 「簽到｜本月 7 天・再 7 天兌換」一行、整張可點 | 手機以這張為主（頂欄放不下） |
| 帳號選單 | 一項「簽到與寶箱」 | 跟「邀請與許願」並列 |
| 比比寶箱分頁頂端 | 「去簽到」按鈕 | 從文章端導回 |

訪客：看得到入口，點開是**預覽**（月曆是空的、節點與獎勵看得到），按「簽到」才要求登入（沿用現有登入流程，登入完回到這個面板）。Pro 許願（現有 `invite.js`）完全不動。

### 2.2 面板形式

- 桌機：置中對話框，寬 720、高隨內容、最大 `min(640px, 90vh)`；不是浮在頂欄下的小浮層（月曆＋節點放不下）。
- 手機（≤640）：**底部面板**（bottom sheet），高 ≤ 92vh，頂端有拖曳條，可往下滑關閉。只用 `html.m4`／`@media (max-width:640px)` 寫手機樣式（`F6`，不准影響桌機），新 CSS 放 `site/m4/20261107-checkin.css` 後跑 `python scripts/m4_css_links.py`。
- 標題「每日簽到」＋標題旁「?」（說明全收進去，`B2`）；不放日期、不重複標題（`B1`、`H1`）。
- 載入時：所有收展項預設收起（`G1`）；只有「月曆」「進度」「簽到鈕」直接可見，因為這是主體。

### 2.3 格子狀態（核心）

月曆用現有 `site/calgrid.js`（財經日曆、ETF 共用）的週日～週六 7 欄格線與週末反灰，**不另寫一套**；簽到狀態疊在它上面。

| 狀態 | 條件 | 外觀 | 可點？ | 無障礙文字 |
|---|---|---|---|---|
| **已簽** | `ci_sign.kind='live'` | 實心主色底（`--accent` 18% 混 `--panel`）＋右下角白底勾 ✓ | 否 | 「11 月 3 日 已簽到」 |
| **補簽** | `kind='makeup'` | 同「已簽」底色＋虛線外框＋左上角小「補」字章 | 否 | 「…（補簽）」 |
| **節點日** | 該格是本月第 3／7／14／20 個簽到日 | 在已簽格右上角疊一枚小徽章（3／7／14／20 的數字） | 點＝顯示「這天達成 7 天節點」tooltip | 「…達成累積 7 天」 |
| **今天・未簽** | 今天且沒簽 | 外框 2px `--accent`；格內小字「簽」；不閃爍 | **是**（等同按簽到鈕） | 「今天，尚未簽到，按下簽到」 |
| **今天・已簽** | 今天且已簽 | 已簽樣式＋外框 | 否 | |
| **空白（過去未簽）** | 今天以前、沒簽、且在本月 | **完全空白**（只有日期數字，`--ink-3`），不加紅字、不加叉 | 平常否；**補簽模式**開啟時變可點（見 §7） | 「11 月 4 日 未簽到」 |
| **未來** | 今天以後 | 日期數字 40% 不透明、無框 | 否 | |
| **非本月** | 補空格的上下月日期 | 不顯示 | 否 | |
| **週末／休市** | `calgrid` 既有 `cg-we`／`cg-hol` | 沿用反灰底與「休市」小字；**照樣可以簽到**（見 §3.1） | 同上 | |

顏色用 `--accent`、`--ink*`、`--panel*`、`--line`；**不使用 `--rise`／`--fall`**（`D3`：紅綠只表示漲跌）。深淺主題只換變數值；對比自己量（已簽格文字 ≥ 4.5:1、徽章 ≥ 3:1）。

### 2.6 互動規則

1. 簽到鈕按下 → 立即 disable＋「簽到中…」（同一次只送一個請求）→ 成功：當天格子 200ms 填色、累積數字更新、toast「今天簽到完成，本月累積 N 天」；若剛好達節點，進度條該點變實心並出現「兌換」鈕。**按了畫面一定要變**（`C11`）；失敗時按鈕恢復並寫一句原因（沒登入／網路／今天已簽）。
2. 簽到判定日期：**台北時間**，以 Worker 回傳的 `today` 為準；瀏覽器時間只用於畫面預排，不作數（防改系統時間）。
3. 切換月份（‹ ›）：只讀、不改版面尺寸（`A9`）；過去月份顯示簽到日與當月兌換紀錄，不能補簽；不能切到未來月份。
4. 休市日與週末照樣可簽：理由見 §3.1。
5. 減少動態偏好（`prefers-reduced-motion`）：填色不動畫。

### 2.7 文案紅線

不寫「別斷」「你失去了」「快補簽」「最後機會」；回到久未簽到的月曆時，只有一句「歡迎回來，本月已累積 N 天」。不顯示任何紅色或警示（研調 5-6、設計意見 §4）。

## 3. 累積節點

### 3.1 計天規則

- **一個月 = 台北時間的曆月。** 每月 1 日 00:00 歸零，只有「本月累積天數」歸零；已兌換的文章、徽章、解鎖紀錄永久保留。
- **曆日都能簽（含週末與休市日）。** 判斷理由：① 現況 `site/tw_holidays.json` 有休市表，但「國定假日名單來源」設計意見仍列為待確認，用交易日計天就要把這份表綁進伺服器判定，錯一天就是客訴；② Andy 的月曆心智模型是整個月的格子；③ 20 天節點在 30 天的月份有 10 天餘裕，加上每月 3 次補簽，勤勞度要求不高。代價：週末簽到的人看到的是「前一個交易日」資料，不影響簽到本身。替代方案見 §17 第 1 題。
- 補簽也計入累積天數，但不重複計入節點日徽章以外的獎勵（不另給）。

### 3.2 節點與理由

| 節點 | 累積天數 | 獎勵（§4） | 依據 |
|---|---|---|---|
| N1 | **3** | 教學包 ×1（2 篇） | 籌碼K線第 3 天放小禮（研調 1-2）；行銷建議「第 3 天徽章」＝先有一個很快到的甜頭，降低第一週流失 |
| N2 | **7** | 教學包 ×1（2 篇） | 行銷第 7 天 A 級券、Duolingo 以 7 天為習慣分界（研調 §3，相關非因果）；一週一個回饋 |
| N3 | **14** | 產業深度包 ×1（2 篇） | 約月中；放比較有份量的內容。行銷原提議第 12 天，Andy 範例是 14，取 14（兩週，好講） |
| N4 | **20** | **許願券**＋月度徽章 | 籌碼K線的大獎節點是第 20 天（研調 1-2），且 20 天≈一個月交易日數；許願是價值最高、最需要「真的在用」才給的獎勵，放最後 |

**判斷（無數據支撐，所以設成可調）：** 預期分布約 N1 60%、N2 35%、N3 18%、N4 8%（占「有簽到過的會員」）。節點數字與補簽所需互動次數都放進 `site/articles/vault/manifest.json` 的 `config` 區塊（§5.5），Worker 讀它；**改設定次月生效**（本月已進行中的人不受影響）。上線第 2 個月若 N4 達成率 < 5%，把 N4 降到 18。

### 3.3 兌換期限

- 文章節點：到達後**永不過期**，隨時兌換（成本為零，且「兌換」是使用者動作，不過期可避免客訴）。
- 許願券：**到達當月起 60 天內**使用（過期作廢、不補發），避免無限囤積；畫面寫出到期日。
- 同一月同一節點只能兌換一次（資料表主鍵 `(uid, month, node)`）。

## 4. 每個節點的獎勵與兌換流程

### 4.1 兌換前提

1. 已登入，且**註冊滿 3 天**（行銷防白嫖建議）；未滿時按鈕顯示「再 N 天可兌換」，累積照算。
2. 該節點已達成、本月尚未兌換。
3. 官方文案：「兌換不需購買任何方案」。

### 4.2 兌換步驟（文章節點 N1／N2／N3）

```
[兌換] ─► 步驟一：選一個系列（最多 3 張卡）
          ┌────────────┐ ┌────────────┐ ┌────────────┐
          │技術指標    │ │籌碼        │ │總經        │
          │KD、RSI     │ │三大法人     │ │FED 與利率   │
          │2 篇・約8分 │ │2 篇・約8分 │ │2 篇・約8分 │
          └────────────┘ └────────────┘ └────────────┘
          ─► 步驟二：確認（「解鎖後不能換，這 2 篇會永久放進你的寶箱」）
          ─► 步驟三：完成畫面
             「已解鎖 2 篇：〈KD 怎麼讀〉〈RSI 的 30 與 70〉」
             [ 去讀（比比寶箱）]  [ 留在這裡 ]
```

- 「系列」＝教學包有三條線：技術指標／籌碼／總經；N3 的產業深度包列出**尚未解鎖的前 3 包**讓人選（每包以產業鏈命名）。每張卡只顯示「該系列對這個人的下一包」，由伺服器算好回傳。
- 卡片的篇名可見（讓人知道買的是什麼），但**本文不在這一步顯示**。
- 若某系列已被這個人全部解鎖，該卡不出現；全部系列都用完 → §5.6。
- 兌換是**單一交易**：寫 `ci_claim`＋`ci_unlock`（兩篇）同時成功或同時失敗；失敗畫面可重試且不會重複扣。

### 4.3 完成後的引導（「告訴他去哪看」）

1. 完成畫面按「去讀」→ 導到 `#articles/vault`，剛解鎖的卡片帶「新」徽章與一次性的亮邊（動畫 600ms，減少動態時改為靜態亮邊）。
2. 精選文章分頁列的「比比寶箱」標籤上，在使用者**下次打開**前一直保留小圓點（點進去才消）。
3. 站內鈴鐺加一則「已解鎖 2 篇，去比比寶箱看」，內含站內連結（沿用 `notices` 的 `#路由` 連結寫法）。

- 站主若要修訂已發佈文章的內文：改 JSON 內容不改 `id`；要「換掉」一篇＝新增新 `id` 並把舊篇標 `retired`（已解鎖者仍可讀，新兌換者不再抽到）。

### 6.1 沿用現有系統（現況）

### 6.2 使用者端

- 對話框：標題「許願」＋「?」；說明（進「?」）與**固定在表單上緣的一行字**：
  「願望不保證一定做得到。若這批願望站主評估後全部無法實作，會送你 Plus 3 天。」
  （這句話是承諾，也是法遵要求的限定條件，**不可省略、不可只放在「?」裡**。）
- 表單：最多 5 列，每列單行輸入（6～200 字），預設顯示 3 列、可「＋再加一個」到 5；下方選填「為什麼需要」一欄（≤ 500 字，整批共用）；送出鈕「送出 N 個願望」。
- 驗證：至少 1 個有效願望（§17 第 11 題決定最少 1 或 3）；每項 ≥ 6 字、同批不得重複、不得與自己過去已送的願望完全相同。
- 送出後：顯示「已送出 N 個願望。站主逐項看過後，會在這裡告訴你結果」；之後在「我的願望」看狀態。

### 6.3 站主端

- 沿用 `#admin/feedback` → 願望清單。簽到願望的內文前綴：`【願望清單】【簽到願望#<批次碼>-<序號>】<願望內容>`，所以現有篩選、狀態下拉、刪除全部直接可用。
- **新增（P1 才做）一個「簽到願望批次」檢視**：把同一批 1～5 項併成一張卡，每項一排按鈕「會做／做不到／已做／不算」＋一個共用回覆框（≤ 200 字，使用者看得到）。「會做」＝既有的 `eval` 狀態、「做不到」＝既有的 `no`、「不算」（重複、空泛、廣告）＝新增 `void`。
- 站主在批次卡按鈕，等同呼叫 `/v1/admin/feedback/set`（P0 階段）或新端點（P1）。

### 6.4 結果與自動送 Plus 3 天

判定規則（**整批**為單位，判斷：避免「5 個願望 = 15 天」的刷法，也讓站主只要有認真考慮就不必送）：

| 該批每一項的狀態 | 結果 |
|---|---|
| 還有任何一項是 `new`（未處理） | 批次「評估中」，不發獎勵 |
| 全部項目都已處理，且**至少一項是 `eval`（會做）或 `done`（已做）** | 使用者收到「站主打算做 X」；**不送天數** |
| 全部項目都已處理，且**沒有任何一項是會做／已做**（全部 `no`；`void` 不計入） | **自動送 Plus 3 天**，單次、冪等（`ci_wish_batch.granted` 旗標） |
| 全部都是 `void` | 不送，顯示「這批願望不在受理範圍」（避免用垃圾願望換天數） |

- 送天數：呼叫既有 `promoGive(user, 'plus', 3, 'ci_wish')`（現況：已付費者自動改記入 `promo_pending`，待續訂時接上；免費者直接 `promoAdd`）。付費者畫面照樣寫「送 Plus 3 天」，內部走待用天數，**承諾不落空**（§17 第 3 題）。
- 上限（防刷）：每帳號每月最多 1 批（因為只有 N4 一張許願券）；終身最多送 30 天（10 批）；註冊未滿 3 天不給。
- 站主處理過程中可隨時改狀態；批次一旦 `granted=1` 就不再因後續改狀態而收回或重複送。
- 使用者端通知：批次判定完成時，鈴鐺一則「你的 N 個願望有結果了」＋「我的願望」紅點。

### 6.5 站主收得到願望的保證

P0／P1 都經 `feedback` 表，站主原本就在看；另在 `docs/feature_proposals/checkin_spec_1107.md` 的驗收清單加一條：**每次送出，站主端 `#admin/feedback` 在 60 秒內看得到新列**（真人操作驗收，見 §16）。是否額外寄 email 通知站主：沿用 `alertmail.js` 現有「新反饋」行為，不另設。

### 7.2 計數規則與成本

| 規則 | 數值 |
|---|---|
| 補簽所需互動次數 | 第 1 次補簽 **5** 次、第 2 次 **7** 次、第 3 次 **10** 次（遞增，落在 Andy 的 5～10 範圍） |

| 補簽進度 | 本月內累積，**月底未用完歸零**（不跨月） |
| 可補的日期 | 本月、今天以前、尚未簽到、且在「帳號註冊日」當天或之後 |
| 補簽是否影響節點 | 計入累積天數；節點達成與兌換規則不變 |

### 7.3 流程

1. 簽到面板「補簽」區顯示：`◔ 3／5　可補簽 0 次`＋「找比比」鈕（收起面板並展開比比環）。

3. 達標 → 簽到面板「可補簽 1 次」並進入**補簽模式**：本月過去的空白格出現虛線框、可點。
4. 點一個空白格 → 確認「補簽 11 月 4 日？」→ 成功後該格變「補」字章、累積天數 +1、補簽次數 +1。
5. 沒有可補的空白日（本月全勤）→ 不累積點數，面板寫「本月每一天都簽到了」。

### 7.4 防刷

- **伺服器判定，不信任前端計數**：前端每次有效互動送 `POST /v1/checkin/bibi {act, seq}`；伺服器檢查最短間隔 8 秒、`act` 不得與上一次相同、當日 ≤ 10、補簽未滿 3 次、本月有空白日。不符合的回 `counted:false`，**不報錯**（不讓腳本知道規則細節）。
- 風險判斷：互動點數可被腳本灌，但一個補簽最多只換「+1 天累積」，每月封頂 3 天，且節點獎勵本身是教學文章（零邊際成本）；這個風險可接受，不做 CAPTCHA。
- P0（本機模擬）：點數存本機，只供驗證流程；正式版才有伺服器判定。

## 14. 資料模型與 API（P1）

```
ci_sign        (uid, day TEXT 'YYYY-MM-DD', kind 'live'|'makeup', at, test INTEGER, PRIMARY KEY(uid, day))
ci_claim       (uid, month 'YYYY-MM', node INTEGER 1..4, at, choice TEXT, badge TEXT, PRIMARY KEY(uid, month, node))
ci_unlock      (uid, article_id, pack_id, node, month, at, PRIMARY KEY(uid, article_id))
ci_bibi        (uid, day, n INTEGER, last_at INTEGER, last_act TEXT, PRIMARY KEY(uid, day))
ci_makeup      (uid, month, pts INTEGER, used INTEGER, PRIMARY KEY(uid, month))
ci_wish_batch  (id TEXT PK, uid, month, created, status 'open'|'decided', outcome 'granted'|'accepted'|'void'|'', granted INTEGER, reply TEXT, test INTEGER)
ci_wish_item   (id TEXT PK, batch_id, feedback_id, seq, text, state 'new'|'eval'|'done'|'no'|'void', decided_at)
```

| 端點 | 輸入 | 輸出重點 | 失敗碼 |
|---|---|---|---|
| `POST /v1/checkin/me` | token | `today`、本月 `days[]`、`n`、`nodes[{n,reached,claimed}]`、`makeup{pts,need,left}`、`unlocked[ids]`、`wish_ticket{until}`、`wishes[]`、`cohort`（`show:false` 時前端不顯示入口） | `auth` |
| `/v1/checkin/sign` | token | `ok`、`n`、`reached_node?` | `already`、`no_visit`、`not_in_cohort` |
| `/v1/checkin/makeup` | `day` | `ok`、`n` | `no_points`、`limit`、`bad_day`、`young_account` |
| `/v1/checkin/bibi` | `act`、`seq` | `counted`、`pts`、`need` | （不報錯，回 `counted:false`） |
| `/v1/checkin/claim/options` | `node` | `options[{line,pack,titles[]}]` 或 `ticket` | `not_reached`、`claimed`、`restocking` |
| `/v1/checkin/claim` | `node`、`line` | `unlocked[{id,title}]` | `young_account`、`conflict`、`restocking` |
| `/v1/checkin/wish` | `items[1..5]`、`why?` | `batch_id` | `no_ticket`、`bad_text`、`young_account`、`too_many` |
| `/v1/checkin/wish/mine` | token | `batches[{items[{text,state}],reply,outcome}]` | `auth` |
| `/v1/admin/checkin/*` | 站主 | 測試與統計 | `forbidden` |

偽碼：兌換（整段在一次交易內）：
```
claim(uid, node, line):
  check reached(node, month) && not claimed(uid, month, node) && account_age >= 3d
  pack = nextPack(uid, line)            // 該 line 中 order 最小且兩篇皆未在 ci_unlock
  if !pack: return restocking
  insert ci_claim; insert ci_unlock for each article of pack  // 主鍵衝突 => 視為已解鎖，回傳既有
  return articles
```
