# 摘要（先看這 18 行）

1. **今天就能用的東西已經做好了**：`site/manifest.webmanifest` 換新、新增 `site/sw.js`、
   新增 `site/icons/`（轉針圖示，192／512／maskable）。
   合上第 ⑩ 節那幾行之後，**手機瀏覽器打開網站 → 分享 → 加入主畫面**，
   就會變成一個全螢幕、有自己圖示、離線也打得開的 App。**不用審查、不用花錢、今天就有。**
2. **★ 最重要的一句話：`site/data/**` 一個位元組都沒有進快取。**
   那是每天盤後重算的資料，快取住等於他打開 App 看到昨天的數字 ——
   **那比沒有 PWA 還糟**。這條我用 Playwright 真的翻過 Cache Storage 驗證（第 ⑨ 節有數字）。
3. **三條路我的建議是「分階段走 1 → 2」，不是三選一**：
   **先 PWA（已完成）→ 再 Google Play（TWA 包裝，幾乎零額外開發）→ iOS 最後做（Capacitor ＋ 原生層）**。
   原生重寫**不要做**，理由在 2-4。
4. **兩個商店的難度差距非常大，這是這份文件最重要的一個發現。**
   **Google 官方支援直接把 PWA 包成 App 上架**（Trusted Web Activity ＋ Bubblewrap，信心：高）——
   我們幾乎不用多寫程式。
   **Apple 明文禁止「只是把網站包起來」**（設計指南 4.2 最低功能性，信心：高）——
   要上 iOS，一定得加一層真的原生東西，否則會被退件。
5. **〔事實〕費用很便宜，難的不是錢**：Apple 開發者 **US$99／年**（約 NT$3,200），
   Google Play **US$25 一次付清、不續費**（信心：高）。第一年合計約 NT$4,000。
6. **〔事實・新帳號的隱藏門檻〕Google Play 個人開發者帳號**（2023-11-13 之後開的）
   **必須先跑封閉測試：至少 12 個測試者、連續 14 天，才能申請正式發佈**，
   申請審核再約 7 天（信心：高）。
   **這是整條路上最長的一段等待，而且花錢也買不到。Andy 要先湊得出 12 個人。**
7. **★★ 最可能讓我們上不了 iOS 的，不是 4.2，是 3.2.1(viii)。**
   〔事實〕Apple：「用於金融交易、投資或資金管理的 App，**應由提供該服務的金融機構提交**，
   並且在上架地區持有必要的執照與許可」（信心：高）。
   **而且舊版允許的「用金融機構的公開 API」這個替代路徑已經被拿掉了**（信心：中）。
   我們不是金融機構、沒有投顧執照。
   **〔判斷〕我們的定位必須寫成「行情與產業資訊工具」，不能寫成「投資建議／選股推薦」**——
   這同時也是台灣《證券投資信託及顧問法》那條紅線的同一件事（見 `docs/product_strategy.md` 摘要第 1 條）。
8. **〔事實〕Google Play 那邊也要填「財務功能聲明」**（Financial features declaration，2023-08-31 起強制），
   而且要遵守目標國家的在地法規與揭露要求（信心：高）。
9. **★ 收訂閱費會連鎖引爆三件事**，不是只有抽成：
   ① 蘋果抽 **30%**（小型企業方案 **15%**，年收入 100 萬美元以下可申請，信心：高）；
   ② **GitHub Pages 使用條款禁止拿它經營線上生意**（信心：高，見 `product_strategy.md`），
   所以收錢就得搬家，而 App 包的就是這個網站；
   ③ **台灣投顧法的「報酬」要件會成立**。
   **〔判斷〕結論：先免費上架，訂閱制留到法遵與搬家做完再談。**
10. **399／799 的實收試算**（第 ⑤ 節有完整表）：
    399 走 App 內購，蘋果標準抽成實收 **NT$279**，小型企業方案 **NT$339**；
    Google Play 訂閱 15%，實收 **NT$339**。**走網頁自己收款實收約 NT$387，但那條路現在走不了**（見第 9 條）。
11. **〔事實〕Apple 審查很快**：平均 24～48 小時，2026 年多數追蹤資料落在「排隊 5～14 小時 ＋ 審查約 1 小時」（信心：中）。
    **慢的是退件重送的輪次，不是單次審查。**
12. **時程**：**里程碑 A（第一版能上架）＝ 實作 5～7 個工作天，日曆時間 5～7 週**，
    瓶頸是 Google 的 12 人 × 14 天與 Apple 的退件輪次。
    **里程碑 B（完整體驗：帳號、推播、跨裝置同步、訂閱）＝ 再 6～10 週，而且要先有後端。**
13. **★ 一個非做不可的前提：Andy 不跑本機指令。**
    所以**所有打包都必須在 GitHub Actions 裡跑**：
    Android（Bubblewrap）跑 Linux runner，iOS（Capacitor）要 **macOS runner**。
    兩個都做得到，簽章金鑰放 GitHub Secrets（**不進 repo**）。
    這一條不解決，後面全部是空談。
14. **〔判斷・要先確認的坑〕TWA 需要 Digital Asset Links**：
    要在**網域根目錄**放 `/.well-known/assetlinks.json` 來證明 App 與網站是同一個人的。
    我們是 `miaozike.github.io/tw-rotation/`（專案頁），根目錄屬於 `miaozike.github.io`，
    **必須另外開一個名為 `miaozike.github.io` 的 repo 才放得進去**（信心：中，這是我從機制推的）。
    **〔判斷〕與其繞，不如直接買一個自己的網域**（約 NT$500～1,000／年）——
    它同時解決品牌、Digital Asset Links、以及未來搬家的問題。
15. **〔判斷〕命名還沒定案，所以這批的 App 名稱先沿用「台股資金輪動儀表板」。**
    `docs/product_strategy.md` 列了 8 個候選、最推薦〈剖面〉，Andy 還沒挑。
    **商店上架之後改名字是可以的，但 App Store 的 Bundle ID 與 Google 的 package name 一旦上架就永遠不能改** ——
    **所以命名要在第一次送審之前決定**，這是硬期限。
16. **〔事實〕iOS 的 Web Push 只在「已加入主畫面」的 PWA 裡才有**（iOS 16.4+，信心：高），
    而且**可靠度有已知問題**（重開機後 SW 事件不一定觸發、使用者會莫名被取消訂閱，信心：中）。
    **〔判斷〕推播這件事，iOS 上要做得可靠就只能走原生，這是 PWA 真正的天花板。**
17. **〔事實〕iOS 對 PWA 的儲存很兇**：不常開的 PWA 快取與 IndexedDB 可能在 **7 天**內被清掉（信心：中高）。
    **對我們反而幾乎無害** —— 我們刻意不快取資料，被清掉只是下次多抓一次殼。
18. **我沒有驗到的部分寫在第 ⑫ 節，請直接看那一節**，不要從上面推。

# ① 起點：我們現在有什麼、缺什麼

**〔事實，信心：高，直接讀 repo〕**

| 項目 | 現況 |
|---|---|
| 產品型態 | **響應式靜態網站**，GitHub Pages 託管，<https://miaozike.github.io/tw-rotation/> |
| 前端 | `site/index.html` ＋ 約 40 支自家 JS（約 2.7MB）＋ `vendor/` 第三方圖表庫（約 1.9MB） |
| 資料 | `site/data/**` 共 31 個 JSON ＋ 個股／歷史目錄，**每天盤後由 GitHub Actions 重算、重新部署** |
| 後端 | **沒有**。唯一的伺服器端是 `workers/quote-proxy/`（Cloudflare Worker，只做即時報價的 CORS 代理） |
| 帳號 | **沒有**。全站設定存在瀏覽器 `localStorage`（22 個鍵） |
| 金流 | **沒有** |
| 推播 | **沒有** |
| 維護人力 | **一個人** |

**這個起點決定了三件事**（〔判斷〕）：

1. **路徑一定是「網站 → 可安裝 → 上架」**，不是從零寫 App。這一點三條路都同意。
2. **「跨裝置同步」「推播」「訂閱」三個商店最看重的 App 特徵，我們一個都沒有** ——
   而缺這三個，正好就是 Apple 4.2 退件的典型畫像。
3. **沒有後端 ＝ 里程碑 B 的每一件事都要先補後端**，那是這條路上最大的一筆工。

# ② 三條路的比較

## 2-0 一眼看完

| | **路線 1：PWA** | **路線 2：WebView 包裝** | **路線 3：原生重寫** |
|---|---|---|---|
| 進得了商店嗎 | ❌ **不在商店裡** | ✅ 兩家都可以 | ✅ 兩家都可以 |
| 要開發者帳號嗎 | ❌ 不用 | ✅ 要（Apple US$99/年、Google US$25 一次） |✅ 同左 |
| 要審查嗎 | ❌ 不用 | ✅ 要（Apple 是主要風險） | ✅ 要 |
| 額外開發量 | **已完成（今天）** | Android 約 0.5 天；**iOS 約 3～5 天**（要加原生層） | **3～6 個月** |
| 原生推播 | iOS 勉強、Android 可以 | ✅ 兩邊都可靠 | ✅ |
| 每次改東西要重新送審嗎 | ❌ 不用，改網站就好 | ❌ **內容改動不用**（殼不動就不用送審） | ✅ 每次都要 |
| 一個人維護得動嗎 | ✅ | ✅ | ❌ **維護三份程式碼** |
| **我的建議** | **✅ 先做（已做）** | **✅ 接著做，Android 先、iOS 後** | **❌ 不要做** |

## 2-1 路線 1：PWA（加到主畫面）

**做法**：`manifest.webmanifest` ＋ Service Worker ＋ 圖示，使用者用瀏覽器的「加入主畫面」安裝。

**優點**
- **成本 0、審查 0、等待 0。** 今天做完今天就有。
- 改版即時生效，不用送審，這對「每天換資料」的產品特別重要。
- **它是另外兩條路的共同底座**：Capacitor 包的是這個網站，TWA 包的也是這個網站。
  所以這一步永遠不會白做。

**缺點（要誠實講）**
- **〔事實〕不在商店裡。** 沒有 App Store／Google Play 的搜尋曝光，也沒有商店評價這個信任背書。
  對「沒有品牌、沒有流量」的我們，**這正是最痛的一點**（`product_strategy.md` 摘要第 6 條）。
- **〔事實〕安裝路徑在 iOS 上又長又難教**：Safari → 分享 → 加入主畫面。
  **而且 iOS 只有 Safari 能裝**（其他瀏覽器裝不了，信心：中高）。轉換率必然很低。
- **〔事實〕iOS 的 Web Push 只在「已加入主畫面」的 PWA 裡有效**（iOS 16.4 起，信心：高），
  且**可靠度有已知問題**：SW 事件在裝置重開後不一定觸發、使用者會莫名被取消訂閱、
  點通知有時開錯網址（信心：中）。
- **〔事實〕iOS 儲存會被回收**：不常開的 PWA，快取／IndexedDB 可能在約 7 天內被清掉（信心：中高）；
  Safari 17 之後有 Persistent Storage API 可以請求豁免，**但那要先拿到通知權限**（信心：中）。
  → **對我們影響很小**，因為我們本來就不快取資料。
- **〔事實〕iOS 對 PWA 的快取上限約 50MB**（信心：中）。我們的殼約 4MB，**不會頂到**。

**〔判斷〕結論**：PWA 解決「手機上用起來像 App」，**解決不了「被找到」與「可靠的推播」**。

## 2-2 路線 2：WebView 包裝

這條路其實**是兩條不一樣的路**，兩個商店的機制完全不同，不能混為一談。

### 2-2-A Android：Trusted Web Activity（TWA）＋ Bubblewrap —— **這是官方支援的路**

**〔事實，信心：高〕** Google 官方提供 **Bubblewrap** 這個命令列工具，
把 PWA 包成 Android App Bundle（AAB）上架 Google Play；它是 Google Chrome Labs 的專案，
會處理 JDK／Android SDK，並支援推播通知委派與定位。
需要 **Digital Asset Links** 驗證網域所有權，並建議 Lighthouse 分數 ≥ 80（信心：中）。

**〔判斷〕為什麼這條路對我們幾乎是白送的**：
TWA 不是 WebView，是「把 Chrome 全螢幕嵌進 App」，所以**網站長什麼樣，App 就長什麼樣**，
不用重排版、不用改一行前端。額外工作只有：打包、簽章、assetlinks、商店素材。

**要注意的**
- **〔判斷，信心：中〕`assetlinks.json` 的位置問題**（摘要第 14 條）：
  必須在 `https://miaozike.github.io/.well-known/assetlinks.json`，
  也就是 **user site 的根目錄**，不是我們的專案目錄。要另開一個 `miaozike.github.io` repo，
  或者買自己的網域。**這一條一定要先驗證，卡住的話整條路會停在這裡。**
- **〔事實，信心：高〕個人帳號的 12 人 × 14 天封閉測試**（摘要第 6 條）。2026 年起 Google 還會檢查
  「這些測試者是不是真的有在用」（信心：中）。
- **〔事實，信心：高〕目標 API 等級**：2026-08-31 起新上架與更新要 **Android 16（API 36）**。
  Bubblewrap 產出的專案要記得跟上，否則會被擋。

### 2-2-B iOS：Capacitor（或同類）—— **這條的關卡是 Apple 4.2**

**〔事實，信心：高〕設計指南 4.2 最低功能性**的原文轉述：
> 「你的 App 應該包含**超越『重新包裝的網站』**的功能、內容與介面。
> 如果你的 App 不是特別有用、獨特或『像 App』，它就不屬於 App Store。」

實務上被退件的畫像（信心：中高，多個來源一致）：
> 「只用 WebView 載入你的網站、什麼都沒加：**沒有原生導覽、沒有離線行為、沒有推播、
> 沒有裝置整合**」→ 被判定為「與用手機瀏覽器逛網站沒有顯著差異」。

**〔事實，信心：中〕怎麼避開**：多個來源一致指出，
「加了原生推播、原生導覽、離線處理、原生購買的 Capacitor App **例行地會過**」。
Apple 退的不是 WebView 本身，退的是**沒有加值的殼**。

**〔判斷〕我們具體要加的原生層（這是 iOS 那 3～5 天工作的內容）**：

| # | 要加什麼 | 為什麼這一條擋得住 4.2 | 工作量 |
|---|---|---|---|
| 1 | **原生底部分頁列**（總覽／資金流向／產業／個股／設定），點了用原生轉場切網頁路由 | 直接對應「沒有原生導覽」這條退件理由；也是審查員第一眼看到的東西 | 1 天 |
| 2 | **原生推播**（APNs）：盤後資料更新完、自選族群進入「漲潮區」時推一則 | 這是 PWA 做不好、原生做得好的那一件事，**最有說服力的加值** | 1～1.5 天（**需要後端派送**） |
| 3 | **原生離線畫面**：斷線時顯示「上次更新時間 ＋ 最後一次看到的結論」，**不是白畫面** | 「網路一斷就白畫面」被明確點名為退件特徵 | 0.5 天 |
| 4 | **原生分享**：把某張剖析圖／某個族群結論分享出去（Share Sheet） | 裝置整合，成本低效益高 | 0.5 天 |
| 5 | **Face ID／Touch ID 鎖住 App**（自選股清單） | 裝置整合；但**要先有自選股功能**，所以排在里程碑 B | 0.5 天 |
| 6 | **Home Screen Widget**（顯示今天四問的結論一行） | 〔判斷〕**最強的一張牌** —— Widget 是網頁在物理上做不到的東西 | 1.5～2 天 |

**〔判斷〕我會在第一次送審就放 1、2、3、4，並在「給審查員的備註」欄裡寫清楚
「本 App 的原生功能有 A/B/C/D，請以這幾個畫面評估」。**
審查員看不到的加值等於不存在，這一欄不要留白。

⚠ **但 4.2 不是 iOS 最大的風險，3.2.1(viii) 才是**（摘要第 7 條、第 ④ 節）。

## 2-3 路線 3：原生重寫（Swift ＋ Kotlin）

**〔判斷〕不要做。** 三個理由，每一個單獨就足以否決：

1. **我們最值錢的東西沒辦法搬過去。** 27 張 2D 剖析圖、19 個 3D 場景、18 張題材圖，
   全部是 ECharts／three.js 的網頁程式碼（`site/dg/`、`site/three3d.js`，約 1.3MB 原始碼）。
   原生重寫等於**這些全部重畫**，而它們正是我們唯一難以被複製的資產。
2. **一個人要維護三份**（網站 ＋ iOS ＋ Android）。
   現況是每天盤後自動重算資料、常常一天改好幾次前端；
   原生的每一次改動都要重新送審，**產品節奏會直接死掉**。
3. **投入完全不成比例**：3～6 個月的工，換到的只有「原生的滑順感」——
   而我們真正缺的是使用者與法遵，不是幀率。

**唯一會讓我改口的情況**：產品變成以**即時交易**為核心（毫秒級報價、下單），
那時 WebView 的延遲與背景執行限制會變成硬傷。**我們離那裡很遠。**

## 2-4 ★ 我的建議

**分階段走，不要三選一：**

```
第 0 階段（已完成，今天）  PWA 底座：manifest + Service Worker + 圖示
        ↓ 合第 ⑩ 節那幾行，部署完就有
第 1 階段（1～2 週工，5～6 週等）  Google Play（TWA）
        ↓ 幾乎零額外開發；卡在 12 人 × 14 天
第 2 階段（3～5 天工 + 送審輪次）  iOS App Store（Capacitor + 原生層）
        ↓ 卡在 4.2 與 3.2.1(viii)
第 3 階段（里程碑 B）  後端 + 帳號 + 推播派送 + 訂閱
```

**為什麼 Android 先、iOS 後**（〔判斷〕）：
1. Android 那條幾乎不用寫程式，**先拿到「我們有 App」這件事**；
2. Google 的 14 天等待可以**跟 iOS 的開發平行跑**，不浪費日曆時間；
3. iOS 的原生層（推播）**需要後端**，而後端還不存在 —— 先做 Android 可以把這個依賴往後推。
