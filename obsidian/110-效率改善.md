## 一、新的工作方式（2026-09-20 起）

### 1. 每個需求進來，先分類再開工，而且**分類要講給 Andy 聽**

| 級別 | 判準 | 做法 |
|---|---|---|
| **S 小改** | 只動版面／文字／顏色，不動資料流，不影響別的頁面 | 直接改，**只跑受影響的那一段驗收**，併進下一次推送 |
| **M 中改** | 動到某一頁的互動或版面結構，可能影響同頁其他元件 | 改完跑該頁 ＋ 相鄰段落 |
| **L 大改** | 動到資料流（`pipeline/`）、共用元件、或會讓別的頁面跟著變 | 一定跑完整一輪；**改之前先講清楚會影響什麼** |

**判斷「後續影響大不大」的機器判準**（不准靠記憶）：
```bash
git diff --name-only <上次 push>..HEAD
```
- 出現 `pipeline/`、`tests/`、`scripts/`（`_uitest.py` 除外）、`requirements.txt`、`.github/`
  → **L 級，一定跑 pytest**
- 只有 `site/**` → 至少 S 級起跳，看改的是單頁還是共用元件
- 改到 `site/index.html` 的 CSS **且選擇器不只一頁在用** → 自動升級成 L

### 2. **批次驗證**（Andy 明確要求）

以前：每一件事都「改完 → 跑完整一輪 → 推」。
現在：**一批 Task 做完到一個段落，才做一次完整驗證，然後一次推。**

- 做的過程中只跑 `--only <受影響段落>`（單段 11～90 秒）
- **agent 不准再跑完整輪** —— 那是重複勞動，完整輪只由 CEO 在推之前跑一次
- Andy 要「優先看結果」，所以**中途可以先推前端改動讓他看**，
  但推之前仍然要跑受影響的段落 ＋ `_preview`（不能推一個壞掉的版面上去）

### 3. 一律記進 [[100-任務板]]

新需求進來**先寫進任務板再開工**。做完一段回來更新：做到哪、花了多久、卡在什麼。
Andy 直接看任務板就知道有沒有漏，不用回頭翻對話。

## 五、T2 `_uitest` 平行化：做完了（2026-09-20）

**17 分 25 秒 → 6 分 24 秒**（`--workers 4`，已設為預設）。

### 怎麼做的

用**多行程**不是多執行緒。理由：Playwright 的同步 API **不能跨執行緒共用**，
一個執行緒要有自己的 `sync_playwright()`。與其在同一個行程裡繞開它，不如直接開子行程 ——
每個 worker 跑的就是**今天已經驗證過的那條路徑**（單行程、依序跑它那幾段），只是段落少一點。
驗收程式最怕的就是改出「假綠」，所以選風險最低的做法。

分工用**最長優先（LPT）**：把最重的段落先放進目前最輕的那一籃。
段落耗時差距很大（實測 3 秒到 133 秒），平均分配的話最慢那一籃會拖垮整輪。
每一輪跑完會把各段耗時記進 `scripts/.uitest_times.json`，下一次分得更平均。

### ★ 怎麼確認沒有假綠

**同一份程式碼各跑一次平行與依序，紅字逐字比對** —— 完全一致（6 條，都是既有的環境限制）。
這一步不能省：平行化最危險的失敗模式不是變慢，是**有些段落沒真的跑到卻報綠**。

### ★ 平行化順便逼出三個潛在缺陷（都修了）

這三個在依序跑時都是綠的，**純粹是因為順序剛好對**：

1. **「族群頁」假設前面已經有人導航過。** 它直接 `fetch('data/groups_detail.json')` 這個**相對路徑**，
   一旦它變成某個 worker 的第一段，頁面還在 `about:blank`，相對路徑解不出來就整段爆掉。
   修法：那一段自己先導航；另外在 runner 加一道防線，每段開始前確保頁面在站上。
2. **「KPI 捲動」假設頁面一開始在最上面。** 前一段把頁面捲到 1592 之後，基準值就錯了。
   修法：點 KPI 之前先捲回頁首 —— 那一排本來就長在頁面最上面，忠於使用者的真實狀態。
3. **★ 一個真的產品 bug**：KPI 的「捲到那張圖」只捲一次，而那一刻圖表還在長高
   （每張圖都有 min-height 佔位，畫完才變成真高度），**使用者被留在錯的位置，
   看起來就像「點了沒反應」**。在慢一點的機器上一定會遇到 ——
   這跟 Andy 回報的 C2「換一台電腦版面就跑掉」是同一類。
   修法：捲過去之後繼續盯著目標位置，還在變就再捲一次，直到位置穩住（有上限，
   而且使用者自己動滾輪就立刻放手，不跟人搶）。

### ★ 順便改掉「睡固定秒數」

新增 `wait_until(pg, expr, timeout)`：輪詢到條件成立為止。
以前到處是 `wait_for_timeout(1400)` —— 單獨跑剛好夠，四個 worker 搶 CPU 就不夠，
於是開始**間歇性假紅**。假紅比慢更糟：它會讓人習慣「紅字先無視」，整套驗收就廢了。
而且睡固定秒數不管快慢都要付滿那幾秒，改成等條件之後快的時候立刻往下走
（光這一項就讓平行輪從 6m54s 再降到 4m54s ～ 6m24s）。

### 怎麼用

```bash
python3 scripts/_uitest.py                 # 預設 4 個 worker
python3 scripts/_uitest.py --workers 1     # 依序跑（懷疑平行化改壞了就用它對照）
python3 scripts/_uitest.py --only 總覽,批次7   # 只跑某幾段（子字串比對）
```
